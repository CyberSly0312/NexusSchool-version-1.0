## 1. Context

NexusSchool currently exposes eight Filament panels for eight role-oriented entry paths. A role-card portal presents role "cards" that link users toward the corresponding panel login routes. Authentication itself is stock Filament password authentication on the existing `web` guard, and panel access is gated by `User::canAccessPanel()`. Tenant resolution for school panels is already host-authoritative: `InitializeTenancyForPanel` resolves the tenant from the exact request host against the registered `domains` table and fails closed before any authenticated-user fallback.

The completed Authentication & Panel Access Architecture Review concluded that the current substrate is safe enough to preserve but structurally incomplete for a unified school login experience. The main issues are not that the existing host-first isolation is wrong; it is that:

* login entry is fragmented across role-specific routes and a role-card portal;
* panel eligibility is implied by the entry URL rather than explicitly presented as server-authorized choices after authentication;
* there is no shared `PanelAccessRegistry` or equivalent single authority for role-to-panel mapping;
* interactive authentication audit listeners, per-account throttling, MFA readiness, revocation handling and strict panel authorization are absent or unproven;
* the family panel group has no relation-based ownership substrate, so parent-child and student-own-record scoping must precede exposure of family data;
* an adjacent API OAuth tenant-binding gap exists in the token/tenant relationship and must be treated as a security dependency, not as part of this ADR's implementation.

## 2. Problem Statement

The platform needs a single, predictable login experience for a school tenant without weakening the host-first tenant boundary that already exists.

The current role-card portal is a navigation aid, not an authorization authority. If it remains the effective entry interface, users can be trained to choose their own role and panel, which obscures the fact that credentials do not grant roles or panels by themselves. Conversely, if login were moved to a central domain, the platform would risk authenticating a user before tenant resolution and would create a path for a wildcard session or a central-domain bypass of school-host isolation.

The decision problem is therefore:

1. How to provide one login entry point per school tenant host while reusing the existing `web` guard, password authentication and host-first tenant resolution.
2. How to make panel eligibility a server-side, database-role-derived decision that survives direct URL access and is revalidated on every request.
3. How to permit multi-panel selection only **after** successful authentication, without introducing role selection before authentication.
4. How to preserve all eight existing panel IDs and paths during the initial migration, while explicitly rejecting three new independent Filament panels and any merge of role permissions.
5. How to add missing authentication and authorization hardening without changing tenant identity rules or exposing family data prematurely.
6. How to sequence the work so that existing accounts, passwords, roles, permissions, school relationships and tenant isolation remain intact.

## 4. Current Architecture

### 4.1 Panel topology

Eight Filament panels exist. The logical groups below are presentation/grouping concepts only; they do not create permission equivalence.

| Logical group | Panel ID | Path | Database role |
|---|---|---|---|
| Management | `school-admin` | `/school-admin` | `school_admin` |
| Management | `director` | `/director` | `director` |
| Management | `secretary` | `/secretary` | `secretary` |
| Management | `accountant` | `/accountant` | `accountant` |
| Staff | `teacher` | `/teacher` | `teacher` |
| Family | `parent` | `/parent` | `parent` |
| Family | `student` | `/student` | `student` |
| Central | `super-admin` | `/super-admin` | `super_admin` only |

The role-card portal links to these panel login routes. The `admin` panel ID is also accepted as a legacy alias for `school_admin` in `canAccessPanel()`, but the documented canonical panel path is `/school-admin`. Unmapped personnel roles such as `vice_director`, `librarian` and `registrar` are denied until an explicit architecture decision is approved.

### 4.2 Authentication

Verified current behavior:

* One shared Laravel `web` guard is used by all panels.
* Stock Filament login performs credential validation and checks `canAccessPanel()` as part of login acceptance.
* Successful login regenerates the session and redirects to the target panel URL.
* `Filament\Http\Middleware\Authenticate` rechecks `canAccessPanel()` on each authenticated request.
* `User::canAccessPanel()` denies inactive users; restricts `super_admin` to the central `super-admin` panel; denies all non-`super_admin` users from the central panel; maps tenant panel IDs to exact database roles; and requires an active school relationship for tenant panels.
* No interactive authentication audit listeners are implemented.
* Login throttling is component/IP-oriented; per-account throttling is not evidenced.
* MFA is documented as a future capability only (`docs/01_Architecture/Authentication.md:213-223`).
* No account-role revocation event handling specific to active sessions is evidenced.

### 4.3 Tenancy

Verified current behavior:

* `config/tenancy.php:13` sets the tenant model to `School`.
* Tenant databases are not used. A single shared schema with `school_id` discrimination is documented at `config/tenancy.php:53-71`; all Stancl bootstrappers are commented out.
* `InitializeTenancyForPanel` is host-authoritative. It resolves an exact registered domain row for the request host; central hosts and unknown hosts return 404; inactive schools return 403; tenancy is initialized once and cannot switch to another school mid-request.
* An authenticated user may only use the panel of the school matching their `school_id`; mismatch returns 403.
* There is no fallback to an authenticated user's school when host resolution fails.
* No session-stored tenant identifier is used.

### 4.4 Data model

* The users table contains `school_id` (`database/migrations/0001_01_01_000000_create_users_table.php:17,32`).
* No `user_school` migration, model or relation exists at HEAD. The DDL in `ARCHITECTURE_REPORT.md:610-627` is a proposed design sketch, not implemented schema.
* Roles and permissions are existing database concepts; this ADR does not introduce role-permission merges.

### 4.5 Adjacent API authentication gap

The architecture review identified an API OAuth tenant-binding gap: token creation and token validation do not bind the token to the tenant context with the same rigor as the school panel host path (`app/Services/OAuthService.php:21-38`; `app/Http/Middleware/ValidateApiToken.php:29-38`). This is a security dependency for Phase 3, not part of the panel-login decision itself.

## 5. Proposed Architecture

### 5.1 Shape of the decision

Introduce one login entry point per registered school tenant host. The gateway is a **login experience and authorization presentation layer** built on the existing authentication substrate. It is not a new guard, not a new tenant model, not a central SSO service, and not a new panel.

```text
School host request
        |
        v
InitializeTenancyForPanel
  - exact domain match
  - central/unknown host => 404
  - inactive school => 403
  - no user-based tenant fallback
        |
        v
Centralized gateway login page (tenant host only)
        |
        v
Existing web guard + password authentication
        |
        v
Session regenerated; host-only cookie
        |
        v
PanelAccessRegistry (server-side)
  - active account
  - database roles only
  - active school relationship
  - central super-admin rule
        |
        v
Post-authentication panel selector
  - only server-authorized panels
  - direct URLs still revalidated
        |
        v
Selected existing panel ID/path
```

### 5.2 Gateway login

The gateway login page must:

* be reachable on a valid tenant host only;
* reuse the existing `web` guard and password authentication;
* never accept a tenant, school, role or panel choice from the login form;
* never infer tenant identity from the authenticated user when host resolution fails;
* preserve existing panel login routes during initial migration;
* redirect after authentication to the post-authentication panel selector, not to a role card chosen before login.

### 5.3 Shared `PanelAccessRegistry`

A shared `PanelAccessRegistry` (or equivalent authorization service) becomes the single server-side authority for role-to-panel mapping.

Registry rules:

| Rule | Requirement |
|---|---|
| Source of truth | Database roles only. No request input, query parameter, hidden field or role-card selection may grant access. |
| Inactive account | Deny all panels. |
| `super_admin` | Central `super-admin` panel only; never a tenant panel. |
| Central panel | Deny every non-`super_admin` role. |
| Tenant panels | Exact role mapping; active school relationship required. |
| Management group | `school-admin`, `director`, `secretary`, `accountant` are logical grouping only. |
| Staff group | `teacher` is logical grouping only. |
| Family group | `parent`, `student` are logical grouping only; data exposure remains deferred. |
| Unmapped roles | Deny until explicit architecture decision. |
| Revalidation | The registry is consulted on every authenticated request through `canAccessPanel()` / panel middleware. |

Initial registry mapping preserves current behavior, including the legacy `admin` alias for `school_admin`:

| Panel ID | Allowed role(s) | Additional invariant |
|---|---|---|
| `super-admin` | `super_admin` | Central only; no school panel access |
| `admin` | `school_admin` | Legacy alias; active school required |
| `school-admin` | `school_admin` | Active school required |
| `director` | `director` | Active school required |
| `secretary` | `secretary` | Active school required |
| `accountant` | `accountant` | Active school required |
| `teacher` | `teacher` | Active school required |
| `parent` | `parent` | Active school required; data exposure deferred |
| `student` | `student` | Active school required; data exposure deferred |
| any other panel ID | none | Fail closed |

`User::canAccessPanel()` becomes a thin delegate to the registry. Its externally observable behavior must be proven unchanged by regression tests.

### 5.4 Post-authentication panel selector

After successful authentication, the user sees only panels for which the registry has already returned `true`. The selector is a presentation of server authorization, not an input to it. A user with multiple roles may see multiple panels; a user with no authorized panel receives a safe denial state that does not reveal unauthorized panel availability.

Direct URL access remains authoritative: visiting `/director`, `/parent` or any other panel URL without authorization must deny access even if the selector would not have shown it.

### 5.5 Tenant isolation

Tenant isolation remains unchanged and stricter than any user-derived approach:

* domain-first resolution remains the only tenant identity source for school panels;
* all existing fail-closed rules remain in force;
* `school_id` ownership checks remain on tenant-owned data;
* no tenant identity is inferred from an authenticated user when host resolution fails;
* no wildcard cookie is introduced;
* no central-domain tenant authentication is introduced;
* the API OAuth tenant-binding issue is tracked as a dependency.

### 5.6 Session and security controls

Proposed controls for later phases:

* host-only session cookies with no `Domain` attribute spanning subdomains;
* `secure` cookie flag in production, `httponly`, and an explicit SameSite policy decided by Architecture and Security;
* session regeneration on authentication and invalidation on logout/revocation;
* per-IP and per-account throttling with audit-safe messaging;
* authentication success/failure/denial audit events with tenant host, user identifier, panel ID and reason, excluding credentials;
* account/role revocation handling that invalidates affected sessions or forces revalidation;
* MFA readiness decision for privileged accounts, with implementation explicitly deferred.

### 5.7 Authorization hardening

Before family data is exposed:

* conduct a policy coverage audit over resources, pages, widgets and actions;
* assess Filament strict authorization and record the decision;
* require explicit resource/page/widget/action authorization rather than relying on panel visibility;
* design and test parent-child and student-own-record scoping;
* keep family panel data unavailable until the substrate passes review.

### 5.8 What this ADR does not change

No new domain, no new panel, no new guard, no new tenant database, no new pivot table, no role merge, no permission merge, no central identity provider, no wildcard session, no sprint authorization and no implementation are created by this ADR.

## 7. Alternatives Considered

| Alternative | Description | Security | Tenant isolation | Migration risk | Governance fit | Decision |
|---|---|---|---|---|---|---|
| **A-1: Existing role-card portal** | Keep role cards as the effective entry interface linking to per-panel login routes. | Moderate. Authorization is enforced by `canAccessPanel()`, but role selection is user-facing before authentication and the experience implies role choice is authoritative. | Strong at request level because host resolution is unchanged, but UX obscures the host boundary. | Lowest; no change required. | No ADR needed, but does not solve the unification problem. | **Rejected as target state.** Acceptable only as a legacy interface during Phase 1-4. |
| **A-2: Centralized tenant-host gateway** | One login page per school tenant host on the existing `web` guard, with server-side registry and post-auth selector. | Strong. Credentials authenticate; registry authorizes; no role input before auth; audit/throttle/revocation can be centralized. | Strongest fit: preserves exact host resolution and fail-closed behavior; no wildcard session; no central bypass. | Moderate; additive routes and registry can preserve existing routes and panel IDs. | Best fit for Architecture Freeze: no new domain, guard, tenant model or panel. | **Recommended.** |
| **A-3: Central-domain SSO** | Authenticate once on a central domain and issue access to school tenants. | Attractive long-term, but creates high-risk token/session boundary; MFA, issuer trust, replay and tenant claim binding would need a separate ADR. | Weakest near-term: risks tenant identity being inferred from a central identity claim or wildcard cookie; conflicts with the current host-authoritative rule. | High; requires new identity protocol, session/token design and domain trust changes. | Requires broader architecture, security and possibly legal/privacy approval. | **Rejected for this decision.** May be reconsidered only in a future ADR. |
| **A-4: Three new independent Filament panels** | Replace logical groups with new Management, Staff and Family panels. | Weakens least privilege: role permissions would have to be merged to populate group panels; family data would be exposed before relation scoping. | Adds new panel paths and middleware/tenant bindings; increases cross-role data exposure risk. | High; new panel providers, routes, resources, tests and migration of users. | Conflicts with current panel topology and the explicit non-goal of no merged role permissions. | **Rejected.** |
| **A-5: Merge role permissions without new panels** | Keep eight panels but give grouped roles overlapping permissions. | Weakens role separation and audit attribution; makes direct URL authorization harder to reason about. | Does not improve tenant isolation. | Moderate but semantically damaging. | Requires RBAC strategy change under Architecture Freeze. | **Rejected.** |

### 7.1 Why the recommended approach is preferable

A-2 is the only option that improves the login experience while reinforcing, rather than replacing, the existing host-authoritative tenant boundary. It avoids inventing a central identity authority, avoids wildcard cookies, avoids merging role permissions, and can be introduced additively while all eight existing panel IDs and paths remain in place. It also gives a natural home for the missing security controls: audit, throttling, revocation and cookie hardening can be attached to a single authentication path while authorization remains per-request and role-derived.

## 8. Security Implications

### 8.1 Security benefits

* Removes user-facing role selection from the pre-authentication step.
* Ensures credentials authenticate a person, not a panel entitlement.
* Centralizes authorization decisions while keeping enforcement per request.
* Preserves fail-closed tenant resolution.
* Reduces the chance of a wildcard session cookie or central-domain bypass.
* Creates a single place to add audit events, throttling and revocation handling.

### 8.2 Security controls required before production

| Control | Requirement | Current status |
|---|---|---|
| Host-only cookie | No cookie `Domain` spanning subdomains. | **PARTIALLY IMPLEMENTED / UNVERIFIED** |
| Secure production cookie | `secure` enabled in production; explicit SameSite policy approved. | **UNVERIFIED** |
| Session regeneration | Regenerate on login. | **VERIFIED IMPLEMENTED** for stock Filament login; gateway must preserve. |
| Session invalidation | Logout and revocation invalidate sessions. | **PARTIALLY IMPLEMENTED / UNVERIFIED** |

| Family scoping | Parent-child and student-own-record checks before exposure. | **NOT IMPLEMENTED** |

### 8.3 Residual risks

Even after the proposed gateway is adopted, the following remain unless separately approved and implemented: MFA, central SSO, tenant-bound API tokens, family relation authorization and full policy coverage. This ADR does not declare them solved.

## 9. Tenant Isolation Implications

The proposed gateway is deliberately tenant-host-scoped. It does not change the tenant model.

Invariants:

1. Tenant identity comes from the exact registered request host only.
2. Central hosts never serve a tenant panel.
3. Unknown or unregistered hosts fail closed with 404.
4. Inactive schools fail closed with 403.
5. Tenancy initializes once per request and never switches tenants mid-request.
6. An authenticated user must match the resolved tenant's key; mismatch is 403.
7. No authenticated-user fallback is permitted when host resolution fails.
8. Every tenant-owned read/write retains `school_id` ownership enforcement.
9. No wildcard session cookie is introduced.
10. No central-domain authentication path bypasses host resolution.
11. The API OAuth tenant-binding gap is treated as a cross-surface isolation dependency.

The gateway must not add cache keys, queues, file paths or selectors that cross tenant boundaries without explicit `school_id` scoping.

## 10. Authentication and Session Implications

### 10.1 Login flow

The login flow after approval would be:

1. User requests a school host.
2. `InitializeTenancyForPanel` resolves and validates the tenant host.
3. Guest sees the centralized gateway login page for that host.
4. User submits credentials to the existing `web` guard.
5. On success, the session is regenerated and a host-only cookie is issued.
6. `PanelAccessRegistry` returns authorized panel IDs.
7. User sees the post-authentication panel selector.
8. Every subsequent panel request revalidates authentication and registry authorization.

### 10.2 Multi-panel behavior

Multi-panel access is derived from multiple database roles. The selector displays only server-authorized panels. No role selection input is accepted before or during authentication. A user with no authorized panels receives a denial state that does not disclose panel inventory.

### 10.3 Session behavior

* Cookies are host-only; no wildcard `Domain`.
* Production cookies must use `secure`.
* Session regeneration remains mandatory on login.
* Logout and revocation must invalidate or force revalidation of sessions.
* SameSite policy is a Security/Architecture decision and must be recorded before Phase 3 production use.
* Session state must not become a tenant identity source.

### 10.4 Revocation and MFA

* Role removal, account suspension and school relationship changes must be handled through an explicit revocation strategy.
* MFA is a readiness decision in this ADR, not an implementation. Privileged accounts are the first candidate group.

## 11. Data Model Implications

### 11.1 No schema change in the core decision

The recommended architecture requires no change to `users.school_id`, no new pivot table and no new tenant discriminator. Initial migration is code/configuration/route-level and additive.

### 11.2 Registry is not a database authority by itself

The `PanelAccessRegistry` is a server-side mapping of existing database roles to existing panel IDs. It must not become a second source of role truth. If a future decision changes role names, panel IDs or role groups, that change requires an explicit ADR or approved change record because it affects RBAC strategy under the Architecture Freeze.

### 11.3 `user_school`

No `user_school` table exists at HEAD. The DDL in `ARCHITECTURE_REPORT.md:610-627` is a future multi-campus sketch only. It must not be cited as implemented schema or as a dependency of this gateway.

### 11.4 Family data

The family group is logical only. Parent-child and student-own-record relationships must be proven before data exposure. If additional schema is required for that authorization, it belongs to a separately approved Phase 4 decision and must remain `school_id`-scoped.

## 13. Rollback Strategy

Because the core decision introduces no data migration, rollback is primarily route, configuration and code-level. Every phase must have a tested rollback before deployment.

| Phase | Rollback approach | Constraint |
|---|---|---|
| 0 | No technical rollback; withdraw or amend the ADR through recorded governance. | Do not silently change status or approvals. |
| 1 | Disable gateway route/feature and continue using existing panel login routes. | Never restore an insecure cookie or central-domain login path. |
| 2 | Revert `canAccessPanel()` delegation to the prior implementation or disable registry-backed selector while preserving direct URL authorization. | Registry rollback must not grant unauthorized panels. |
| 3 | Revert config/code for throttle, audit and cookies to the last approved secure baseline. | Security constraint: no rollback to wildcard cookies, disabled tenant binding without waiver, or unlogged privileged authentication. |
| 4 | Disable family data exposure and keep relation-scoped features behind the authorization gate. | Never roll back to unrestricted parent/student data visibility. |
| 5 | Restore legacy role-card interface routes and remove the retirement change. | Only if approved before retirement; after data/config retirement, use documented recovery procedure. |

**Security floor:** a rollback may restore the previous *approved* behavior, never an unapproved insecure state. Any emergency exception requires a recorded Security waiver and compensating control.

### A.2 `ARCHITECTURE_FOUNDATION_REPORT.md:150-155`

## 1. Context

SPR-017 (Archive & Cloud Storage Platform) requires an architecture decision before any implementation may begin. SPR-017's purpose is the **long-term archive and retention of official academic records** produced by the SPR-012 (Academic Communication Engine) substrate and traced by the SPR-014 (Records Lifecycle Management Engine) envelope, plus - in a later, non-mandatory increment - the **provision of downloadable school archive packages**.

The SPR-017 discovery / architecture decision board report (`docs/docs/00_Project_Management/SPR-017_Archive_Cloud_Storage_Decision_Board_Report.md`, 2026-10-10) established substrate facts. The 2026-11-05 governance reconciliation and the 2026-11-06 architecture review re-verified them against HEAD `d42dbef`. This revision uses the re-verified evidence.

### 1.1 Substrate facts verified at HEAD d42dbef

* **No archive implementation exists.** `app/Domains/` contains no `Archive` bounded context. `config/` contains no archive, cloud, storage-abstraction, retention or archive-backup configuration. `database/migrations/` contains no archive, quota or retention table. `routes/` has no archive route. `App\Domains\Archive` is absent.
* **Storage substrate today is local-first.** `config/filesystems.php` defines stock `local`, `public` and `s3` disks. The default disk is `env('FILESYSTEM_DISK', 'local')` (`config/filesystems.php:16`). The `local` disk root is `storage_path('app/private')` (`:35`); the `public` disk root is `storage_path('app/public')` (`:43`); `s3` is defined but unused at `:50`. `config/tenancy.php` suffixes `local` and `public` per tenant (`:140-141`); `// 's3'` is commented out of the tenant disk list at `:142`. The single document storage switch is `config('nexus-academic-communication.disk', env('NEXUS_DOCUMENT_DISK', 'local'))` (`config/nexus-academic-communication.php:25`).
* **Official immutable documents are written today under** `documents/{school_id}/{...}-v{n}.pdf` (and `-delivery-{n}.pdf` delivery copies) via `Storage::disk(config('nexus-academic-communication.disk', 'local'))` (`GenerateDocumentAction.php:212`, `RegenerateDocumentAction.php:88`, `PdfExportChannel.php:72`). The `school_id` in the path is a partition key, not by itself an authorization proof.
* **File metadata exists without verification on read.** `generated_files` stores `school_id`, `file_path`, `file_name`, `disk`, `mime_type`, `size_bytes`, `checksum` and `is_current` (`database/migrations/2026_08_06_000010_create_generated_files_table.php:15-25`). SHA-256 is written at generation (`GenerateDocumentAction.php:236`, `RegenerateDocumentAction.php:118`, `PdfExportChannel.php:90`), but no verification-on-read or scheduled integrity job exists. `size_bytes` defaults to `0`; `disk` is a free string; `checksum` is required. File rows cascade on tenant/document delete (`:29-31`).
* **The lifecycle substrate SPR-017 consumes is SPR-014.** `RecordLifecycleState` expresses exactly three states - `registered | published | archived` - with the transition matrix `Registered->Published`, `Registered->Archived`, `Published->Archived` (`app/Domains/RecordsLifecycle/Domain/Enums/RecordLifecycleState.php`). There is **no** `read_only` or `cold_storage` state; `ARCHITECTURE_DECISIONS.md` section 12's "Cold Storage" stage has no state representation today. `RecordLifecycleService` exposes `register` / `publish` / `archive` / `findBySource`; persistence is the `record_lifecycles` table (`database/migrations/2026_08_10_000000_create_record_lifecycles_table.php`).
* **The published lifecycle contracts are write-only.** Every `RecordsLifecycleContract` in the source domains exposes only `register`, `publish` and `archive` (for example `app/Domains/AcademicCommunication/Domain/Contracts/RecordsLifecycleContract.php:22,36,46`). There is no read/list/query contract and no archive-safe projection. `RecordLifecycleService::findBySource()` is school-scoped but returns the `RecordLifecycle` model, which Archive Domain/Application code must not import.
* **No Academic Communication read contract exists for archive.** `AcademicCommunicationService` exposes commands only (generate/review/approve/publish/archive/regenerate). The only read-only Academic Communication contract is `AcademicDocumentVerificationContract::stateForDocument()`, whose projection is strictly verification-relevant. A read-contract pattern does exist elsewhere: `AcademicPolicyQueryContract` returns read-only, school-scoped reference DTOs.
* **SPR-014 is code-implemented but governance-DEFERRED.** All three source domains (Academic Communication, Report Card, Class Council) register / publish / archive lifecycle metadata through their `RecordsLifecycleContract` adapter seams. Targeted tests are recorded as passing in the 2026-11-05 reconciliation (6 unit tests / 19 assertions; combined targeted run 143 tests / 981 assertions, 89.14 s). The full repository suite was not re-run. `SPR-014_Records_Lifecycle_Engine_Report.md` ends at line 475 with no formal review approval, staging deployment record or closure decision. SPR-014 must remain **DEFERRED**, not COMPLETE.
* **`plans.storage_limit` is a data field, not a quota mechanism.** It is a string column with default `'1GB'` (`database/migrations/2026_07_24_000001_create_plans_table.php:23`). Seeded values are `500MB`, `2GB`, `10GB`, `50GB` (`database/seeders/PlanSeeder.php:25,40,55,70`). `app/Models/Plan.php` lists it as fillable only; there is no cast, parser, accessor, metering, aggregation or enforcement service. A school is linked to a plan only through `subscriptions` (`school_id`, `plan_id`, `starts_at`, `expires_at`, `status`; `database/migrations/2026_07_24_000002_create_subscriptions_table.php:13-17`). `School` has no direct plan relation.
* **Audit exists generically and per-document, but archive audit does not.** `audit_logs` exists (`database/migrations/2026_07_17_000070_create_audit_logs_table.php`). `docs/03_Database/Audit.md:74-79` states audit logs are immutable with a minimum seven-year retention. `SystemCleanupCommand` defaults to `--days=90` and deletes `AuditLog`, `ActivityLog` and `SystemHealth` rows older than the threshold (`app/Console/Commands/System/SystemCleanupCommand.php:14,23-29`); it is scheduled daily (`bootstrap/app.php:47`). `document_audits` is an append-only journal but cascades on school/document deletion (`database/migrations/2026_08_06_000009_create_document_audits_table.php`). No archive event catalogue or archive audit sink exists.
* **No application-level encryption at rest is evidenced.** The local disk stores plain files. `config/database.php:113` has `// 'encrypt' => env('DB_ENCRYPT', 'yes')` commented out. No `Crypt`, `Encrypter` or `openssl_encrypt` usage was found in application code. Host or volume encryption is **UNVERIFIED**.
* **Backup implementation is partial and its documentation overstates it.** `docs/08_Deployment/Backups.md` describes PostgreSQL, uploaded files, school documents, configuration, Docker volumes and logs; daily/weekly/monthly schedule; encryption before storage; 30d/12w/12m retention; off-site copy; RTO < 2h and RPO < 15m. `BackupService::executeBackup()` writes a `.sql` file containing table comments and placeholder `CREATE TABLE` statements, with no data dump, no file copy and no encryption (`app/Domains/System/Services/BackupService.php:46-97`). `restore()` only dispatches `BackupRestored` (`:99-107`). `system:backup` is not scheduled in `bootstrap/app.php`. Backup is **PARTIALLY IMPLEMENTED**; its encryption, off-site copy and restore capability are **UNVERIFIED** or **NOT IMPLEMENTED**.
* **No archive permission surface exists.** `app/Domains/Permission/Enums/PermissionGroup.php` has no `Archive` case. Archive cannot reuse `document.*` semantics; the capabilities differ.
* **No legal retention or data-residency evidence exists.** Repository references to Burkina Faso and Ghana are academic-framework examples, not records law or data-protection law. No data-protection impact assessment, DPA, sub-processor list, hosting-region record or country-specific residency requirement was found.
* **Backup is a separate concern.** Archive/retention is a records-management concern and must not duplicate the backup pipeline. Archived objects must nevertheless remain in backup scope. Backup retention is not archival retention.
* **The legacy document pipeline is excluded.** `app/Models/GeneratedDocument.php`, `app/Models/DocumentTemplate.php`, `app/Services/DocumentGenerationService.php`, the legacy `app/Domains/Document/` context, legacy DocumentCenter views and the legacy `pdf_enable_qr_code` affordance are deprecated and must not be revived, extended or reused - a fixed constraint inherited from ADR-021/022 (L1-L3).
* **ADR numbering.** `docs/ADR/` holds ADR-001 to ADR-022; ADR-023 is reserved by SPR-016 Phase 6B (`SPR-016_Phase6B_Verification_Issuance_Report.md` section 7) for the deferred verification-issuance boundary decision. This ADR therefore uses the next collision-free number, ADR-024. The separate legacy scheme in `docs/06_ADR/` is a different convention and is not extended.
* **Coefficient-index note corrected.** Earlier versions of this ADR cited a 65-character unique index on `coefficients`. The current migration explicitly names the index `coefficients_school_class_subject_unique` (40 characters) at `database/migrations/2026_08_01_000011_create_coefficients_table.php:27`; commit `1696851` (2026-10-15) corrected it. The defect is **resolved / not applicable at HEAD**. The historical note is retained in section 36 only as reconciliation history.
* **S3 line reference corrected.** Earlier versions cited `config/tenancy.php:115`. The actual commented `// 's3'` is at `config/tenancy.php:142`.

## 2. Problem Statement

Before implementing SPR-017 the architecture must be decided for:

1. **Scope / phase placement (PA-1):** is SPR-017 a Phase 3 Academic Records deliverable or a Phase 9 Enterprise Services capability?
2. **Storage strategy (PA-2):** local-first with cloud deferred; which seam keeps a future cloud adapter possible without requiring a provider today?
3. **Archive domain boundary:** is a new bounded context `App\Domains\Archive` the right shape, consuming SPR-014/SPR-012 only through contracts?
4. **Domain integration contracts:** which existing contracts are usable, which must be added, and what projections may Archive read? The contracts named in version 1.0 do not exist as read contracts.
5. **Archive metadata model:** what does Archive own, what is the idempotency key, and how are immutability, soft delete and tenant deletion handled?
6. **Storage port and adapter boundary:** how is local storage accessed without leaking `Storage::disk()` or a provider SDK into Domain/Application code?
7. **Cold-storage trigger and state model:** does the platform add explicit `Read Only` / `Cold Storage` stages, or treat SPR-014 `archived` as the trigger?
8. **Storage quotas:** `plans.storage_limit` is a string data field. What is the canonical unit, school-level resolution, usage measurement, enforcement mode, plan-change behaviour and concurrency model - without inventing a second quota authority or billing policy?
9. **Retention:** what is the configurable mechanism for categories, school policy, eligibility, legal hold, destruction authorization, permanent deletion and audit evidence - without inventing country-specific periods?
10. **Audit:** what is the Archive event catalogue, and how is the documented seven-year audit retention reconciled with the scheduled ninety-day cleanup?
11. **Security:** what controls are required for tenant isolation, authorization, private file access, download, integrity, encryption at rest, key management, backup, restoration and auditability - and which are verified today?
12. **Cloud and data residency:** what conditions must hold before cloud activation, without selecting a provider or region on behalf of the project owners?
13. **Downloadable packages:** whether in scope, who may request, and the security boundary.
14. **Backup versus archive:** archive/retention distinct from operational backup, while archived objects remain recoverable.
15. **Legacy pipeline exclusion:** no revival of the legacy generated-document pipeline.
16. **Decision-log reconciliation:** version 1.0, the SPR-017 board report and `SESSION_HANDOFF.md` disagree on decision numbering, approval status and which open decisions block acceptance.

This ADR is a **decision-only artifact**: no code, models, migrations, controllers, routes, services, permissions, configuration or UI. Implementation is deferred to the SPR-017 implementation phase and must remain within the constraints recorded below.

## 3. Decision Summary

**SPR-017 is a Phase 9 Enterprise Services capability** (PA-1, product-approved) that may be **prioritized for planning now** while its strategic classification remains Phase 9. Storage is **local-first; cloud storage and every cloud-related decision are deferred** (PA-2, product-approved).

The archive is a **new bounded context `App\Domains\Archive`** that consumes source domains and the SPR-014 lifecycle **through read contracts only**, never creates or owns business records, never replaces Records Lifecycle, and records its own archive provenance and retention mechanism.

The **`archived` state of SPR-014 is the trigger** for archive entry. This ADR does **not** invent `Read Only` / `Cold Storage` lifecycle states; that extension is deferred (DR-23).

**Retention policy is configurable per document type, per jurisdiction and per school** (PA-3). The mechanism is specified here; the values are owned by Product/Legal and remain unapproved. Automatic secure destruction is **disabled by default** and is not implemented in the first release.

**`plans.storage_limit` remains the single authoritative plan limit** (PA-4). This ADR explicitly states that the column is **not** a functioning quota mechanism. It specifies a quota contract, canonical bytes, deterministic subscription resolution and a **`report_only`** first release. Metering, enforcement and paid extensions are deferred to pre-production gates.

**Downloadable school archive packages are in architectural scope but not mandatory for the first release** (PA-5). Their security boundary is fixed; their format and mechanics are deferred (DR-24).

Archive and backup remain **separate pipelines**, but archived objects and metadata must be included in backup scope and a restore drill must be recorded before production.

Storage is expressed as a **provider-neutral `StoragePort`** with a local adapter first. S3 compatibility is an optional future adapter, not a mandatory seam. No cloud provider, region, account, credential, SDK, IAM policy, bucket or SLO is introduced by this ADR.

**This ADR does not accept itself.** It records proposed decisions, their owners, their gate classification and the evidence each requires. Acceptance remains an Architecture Team decision after review. SPR-014 remains DEFERRED. SPR-017 remains NOT IMPLEMENTED and NOT AUTHORIZED.

## 4. Decision 1 - Scope and Phase Placement

**Chosen (PA-1, product-approved on 2026-10-10): SPR-017 is a Phase 9 - Enterprise Services capability. It may be prioritized for planning now; its strategic classification stays Phase 9.**

Rationale and consequences:

* The `MASTER_ROADMAP.md` Phase 9 module list ("Cloud Archive / Backup / Disaster Recovery") is the strategic home of archive. The earlier sprint handoff listing of SPR-017 was an implicit Phase 3 implication, corrected by this decision and reconciled in `MASTER_ROADMAP.md`.
* "May be prioritized for planning now" means the architecture board may undertake SPR-017 planning/ADR work at any time. It does **not** make archive an ordinary Phase 3 academic-records sprint, does **not** change the roadmap phase order, and does **not** start implementation without a separate implement-readiness decision.
* The status of Phase 3 deliverables is unaffected: SPR-014 remains DEFERRED, SPR-015 remains implemented with ADR-021 Proposed, SPR-016 remains in progress with Phase 6B deferred.
* SPR-017 planning must not be blocked by a Phase 3 gate; equally it must not be used to reopen, accelerate or silently complete SPR-014.

**Decision status:** APPROVED (existing product-owner record). Implementation status: not applicable.

## 5. Decision 2 - Storage Strategy: Local-First, Cloud Deferred

**Chosen (PA-2, product-approved on 2026-10-10): local-first storage; cloud storage is deferred and every cloud activation is gated.**

The archive platform's first release **must operate entirely on the existing local-first substrate** (`local` / `public` tenant-suffixed disks; documents already stored under `documents/{school_id}/...`). Archived official documents use the **private** disk only. No cloud account, provider, region, credentials, SDK, config key, IAM policy or infrastructure is created, required or preconditioned by this ADR.

Consequences and boundaries:

* The archive domain must keep a **decoupled, provider-neutral storage seam** (Decision 6), so a future cloud object-store adapter can be added without touching domain logic. The seam is **not** an S3 commitment.
* **Cloud activation is gated.** Cloud storage may be enabled only when every condition in Decision 13 is recorded and approved. Until then, "cloud archive" exists only as an abstract, provider-neutral capability.
* No unsupported availability, durability, cost, residency or compliance statement is made anywhere in SPR-017.
* Mixing today's local document storage into an "archive platform complete" claim is explicitly rejected: local document storage is a substrate, not the archive platform.

**Decision status:** APPROVED (existing product-owner record) for the strategy. Cloud activation decisions remain PROPOSED/DEFERRED as recorded in Decision 13.

## 6. Decision 3 - Archive Bounded Context and Closed Ownership

**Chosen (Architecture proposal): a dedicated bounded context `App\Domains\Archive`, consuming source domains and SPR-014 through read contracts only.**

**Implementation status: `App\Domains\Archive` does not exist. This decision is PROPOSED and is not an implementation claim.**

### 6.1 What Archive owns

| Archive owns | Purpose |
|---|---|
| `archive_entries` (provenance and object pointer) | Link a lifecycle record to its archived object and archived metadata. |
| `archive_retention_policies` (mechanism only, no legal values) | Store configurable policy scopes, disposition class, effective dates and legal-basis reference supplied by authorized owners. |
| Archive audit events (dedicated `archive_events` stream or an approved equivalent) | Append-only evidence of archive, retention, hold, disposition, access and integrity events. |
| Retention evaluation outcomes and dry-run reports | Evidence that a policy matched and what would happen. |
| Package request/job metadata (deferred) | Track a future package without implementing it. |
| Archive operational configuration (no secrets) | Non-secret operational settings only. |

### 6.2 What Archive may read, through contracts only

| Archive may read | Source owner | Contract |
|---|---|---|
| Archived lifecycle state and source identity | SPR-014 Records Lifecycle | `ArchivedLifecycleReadContract` (TO BE ADDED) |
| Document identity, type, number, status and current version identity | SPR-012 Academic Communication | `ArchiveDocumentReadContract` (TO BE ADDED) |
| Current file pointer and integrity metadata | SPR-012 Academic Communication | `ArchiveFileReadContract` (TO BE ADDED) |
| Plan/subscription quota projection | SaaS/platform layer | `StorageQuotaContract` (TO BE ADDED) |
| Tenant and authorization context | Shared kernel / Permission | Existing platform authorization surface |
| Audit sink append capability | Audit infrastructure | `ArchiveAuditContract` (TO BE ADDED) or an approved equivalent |

### 6.3 What Archive must never own or mutate

* `record_lifecycles` (SPR-014 owns lifecycle state).
* `academic_documents`, `academic_document_versions`, approvals, signatures and document status.
* `generated_files` (SPR-012 owns storage records).
* Verification identities, certificates and transcripts.
* Any source-domain state transition.
* Backup, restore or disaster recovery.
* The legacy generated-document pipeline.

### 6.4 Prohibited behaviours and imports

Archive must not:

* generate, render, number or publish documents;
* call `RecordLifecycleService::register()`, `publish()` or `archive()`;
* import `RecordLifecycle`, `AcademicDocument`, `AcademicDocumentVersion`, `GeneratedFile`, verification or certificate models into Domain/Application code;
* own a second lifecycle state machine or second quota authority;
* decide academic validity, grades or personal data;
* expose a public or unauthenticated file URL;
* delete source records;
* revive `App\Models\GeneratedDocument`, `App\Models\DocumentTemplate`, `App\Services\DocumentGenerationService`, `App\Domains\Document`, DocumentCenter views or `pdf_enable_qr_code`.

**SPR-014 hardening observation (review O-2).** `ArchiveRecordLifecycleAction` is unscoped by school and skips policy when the actor is null. This is a source-domain defect carrier, not an Archive-owned defect. Archive must never call it. A separate SPR-014 hardening task may be warranted; it is not part of SPR-017.

**`Archive -> Business logic` remains forbidden** (`DEPENDENCY_MAP.md` sections 13 and 15).

**Decision status:** PROPOSED (DR-03), pending Architecture Team approval.

## 7. Decision 4 - Domain Integration Read Contracts

**Chosen (Architecture proposal): Archive consumes SPR-014 and SPR-012 through named, read-only contracts that return tenant-scoped immutable projections. No contract exposed today provides an archive-safe read surface. This ADR does not create the contracts.**

### 7.1 Capabilities Archive needs

| Capability | Minimum fields | Source owner | Why Archive needs it |

## 9. Decision 6 - Storage Port and Adapter Boundary

**Chosen (Architecture proposal): a provider-neutral `StoragePort` with a `LocalStorageAdapter` first. S3 compatibility is an optional, gated future adapter, not a precondition. No adapter exists today.**

**Implementation status: local-first storage VERIFIED IMPLEMENTED; provider-neutral abstraction NOT IMPLEMENTED; cloud activation NOT IMPLEMENTED.**

### 9.1 Current state (verified)

* Local disk root: `storage_path('app/private')` (`config/filesystems.php:35`).
* Public disk root: `storage_path('app/public')` (`:43`).
* Tenant suffixing: `local` and `public` (`config/tenancy.php:140-141`); `s3` commented at `:142`.
* Document disk switch: `config/nexus-academic-communication.php:25`.
* No storage abstraction: direct `Storage::disk()` calls.
* S3 is defined but unused (`config/filesystems.php:50`).

### 9.2 Proposed `StoragePort`

| Operation | Semantics | Notes |
|---|---|---|
| `put(disk, path, stream, options)` | Write a new object | Reject overwrite of an existing archive path by default |
| `getStream(disk, path)` | Read a stream | No public URL; caller must have authorization |
| `exists(disk, path)` | Existence check | Used before metadata reconciliation |
| `delete(disk, path)` | Delete an object | Disabled in first release; separate gated capability |
| `checksum(disk, path, algorithm)` | Compute digest | SHA-256 default; used for verification |
| `size(disk, path)` | Object size | Compare with stored metadata |

**Rules:**

* Domain and Application code depend on `StoragePort`, never on `Storage::disk()` or a provider SDK.
* The port receives a logical disk name from an allow-list (`local`, and later an approved cloud disk). It must never accept a raw path from an HTTP request.
* The first adapter is `LocalStorageAdapter` on the existing tenant-suffixed private disk.
* A future `S3CompatibleStorageAdapter` is optional and gated by DR-20. The port is not an S3 commitment.
* No credentials, bucket names, regions or endpoints are introduced by the ADR.

### 9.3 Proposed archive path scheme

`archive/{school_id}/{document_type}/{academic_year}/{document_number}-v{n}.pdf`

* `school_id` comes from the resolved tenant, not user input.
* `document_number` and `document_type` are validated against the document projection.
* Path components are normalized and rejected if they contain traversal sequences, absolute paths or unexpected separators.
* The path is a partition key, never an authorization proof.

### 9.4 Consistency and failure behaviour

* Metadata write and object write are not a single ACID transaction across storage and database. Use: write object -> compute checksum -> persist metadata in a transaction -> mark entry `active`. If metadata persistence fails, the orphan object is recorded for cleanup, not silently ignored.
* If the object is missing at read time, mark the entry `missing`, audit the event and fail closed.
* If the checksum mismatches, mark `quarantined`, audit and refuse download.
* Disk unavailable or full: fail the operation with a typed error; never produce a partial success entry.
* Soft-delete metadata only in the first release; no physical deletion.

**Decision status:** PROPOSED (DR-05), pending Architecture Team and Security Lead approval.

## 10. Decision 7 - Lifecycle Trigger and Cold-Storage Interpretation

**Chosen (Architecture proposal, partial): SPR-014's `archived` state is the trigger for archive entry. Explicit `Read Only` / `Cold Storage` lifecycle stages are NOT introduced by this ADR.**

* The platform's only existing lifecycle signal is `RecordLifecycleState = registered | published | archived`. Treating `archived` as the archive trigger keeps one lifecycle authority and avoids duplicating state machines.

A future extension requires a lifecycle-authority amendment or successor ADR.
* Consequences of the partial choice: archive may safely run on `archived` records immediately; a future lifecycle extension is additive and would be a separate ADR (ADR-024 amendment or successor), never a silent modification inside SPR-017.

**Decision status:** PROPOSED for the trigger. `read_only` / `cold_storage` extension is **DEFERRED** (DR-23, MAY BE DEFERRED).

## 11. Decision 8 - Storage Quota Architecture

**Chosen (PA-4 product-approved authority + Architecture mechanism): `plans.storage_limit` is the single authoritative plan data field. It is not an implemented quota mechanism. SPR-017 creates no second quota authority. The first release is report-only.**

### 11.1 Existing versus proposed

| Layer | Existing | Proposed | Classification |
|---|---|---|---|
| Plan limit data | `plans.storage_limit` string, seeded values | Keep as authoritative plan field | **VERIFIED IMPLEMENTED** (data field) |
| Unit parsing | None | Strict parser to bytes; binary/decimal decided by owner | **PROPOSED** |
| School -> plan resolution | `subscriptions` table only | Deterministic resolver contract | **PROPOSED** |
| Usage measurement | No aggregation; `generated_files.size_bytes` per file | Report-only projection first | **PROPOSED** |
| Enforcement | None | Deferred until DR-08; `report_only` first | **PROPOSED** |
| Pricing/paid extension | None | Out of scope; Product/Finance | **NOT IMPLEMENTED** |
| Second quota authority | None (correct) | Prohibited | **CONSTRAINT** |

**Truth statement.** `plans.storage_limit` is a free-text column with seeded strings. No cast, parser, accessor, resolver, aggregation, threshold evaluation or enforcement point exists. Saying "quotas reuse `plans.storage_limit`" is true only as a data reference. It is not a working quota system and must not be described as one.

### 11.2 Unit definition

* Canonical internal unit: **bytes** (unsigned integer, 64-bit).
* Parser accepts `B`, `KB`, `MB`, `GB`, `TB`, case-insensitive, optional whitespace.
* **DR-06 must choose binary (1024) or decimal (1000)** and state it explicitly. This ADR does not choose on the owners' behalf. The current seeded strings (`500MB`, `2GB`, `10GB`, `50GB`) have no documented base.
* Invalid, negative, empty or over-precision values fail validation at plan write time and fail closed at read time.
* Display formatting is a presentation concern; it must not change the canonical value.
* Numeric plan limits should eventually be stored as bytes or a validated value object; the string column can remain for compatibility if the parser is authoritative.

### 11.3 School-level quota

* Quota is always resolved per school.
* Plan rows are global; the school's active subscription supplies the plan.
* Archive stores no quota value and no usage ledger.
* A school with no plan/subscription receives `limitBytes = null` and `enforcementMode = report_only` with an explicit `reason`. It must not be treated as unlimited by accident; the null must be visible and audited in quota reports.

### 11.4 Subscription resolution (proposed default)

1. Select subscriptions for the school where `status = active`, `starts_at <= onDate`, and (`expires_at` is null or `expires_at >= onDate`).
2. If more than one matches, choose the latest `starts_at`; tie-break on latest `expires_at`, then latest creation timestamp. Record the tie-break in the audit/report.
3. If none are active, select the most recent expired subscription for **report-only visibility** and mark it `expired`.
4. If none exists, return `limitBytes = null`, `usedBytes` as computed or null, `enforcementMode = report_only`, `reason = no_subscription`.
5. Suspended/cancelled subscriptions never grant capacity; they may still be reported.
6. The resolver is owned by the SaaS/platform layer, not Archive.
7. A future change to subscription semantics must update the contract, not Archive code.

This is a proposed default pending Product/Architecture approval (DR-06, DR-07). The consequence of not deciding is an ambiguous quota read when a school has multiple, expired or suspended subscriptions.

### 11.5 Usage measurement

First release is **report-only**:

* `used_bytes` may be `null` when metering does not exist.
* If computed, the minimum inputs are `generated_files.size_bytes` for the school plus archive object sizes.
* Deduplication rule must be explicit before metering: count each physical byte once per school using a stable identity (source file id + archive entry id), or count archive copies separately if Product decides archiving consumes quota.
* No blocking of archive operations in the first release.
* Usage reporting must be tenant-scoped and must not leak another school's totals.

### 11.6 Enforcement points (future, after DR-08)

Candidate enforcement points, to be decided:

* archive entry creation (the primary new write path);
* document generation (existing SPR-012 write path, outside Archive);
* manual administrative upload (if one is ever added);
* restore/export package generation (deferred).

Archive must not become the enforcement authority for the whole platform. If enforcement is added, it belongs to the platform/SaaS layer and Archive calls the contract before accepting a new object. The contract must define a consistent failure mode (reject, queue or warn) and race handling.

### 11.7 Plan changes and over-quota behaviour

* Upgrade: immediate; new limit applies from the confirmed change date; no data deletion.
* Downgrade: applies at the documented effective date; existing usage may exceed the new limit. The school becomes over-quota but data is not deleted automatically.
* Expiry/suspension: reads remain available per the subscription policy; new archive writes may be blocked only if Product chooses hard enforcement.
* Over-quota first-release behaviour: report and notify; do not block.
* Over-quota future behaviour: decide `soft_limit` (warn and allow) versus `hard_limit` (reject new writes) per operation. Reads and legal/retention operations must never be blocked by quota.
* Paid extension: Product/Finance decision; not an Archive feature.

### 11.8 Concurrent uploads and consistency

* Usage is eventually consistent unless a reservation mechanism is added.
* If hard enforcement is later required, use an atomic reservation/ledger in the SaaS layer (`reserve`, `commit`, `release`) or a database transaction with row locking. Do not rely on a read-then-write check in Archive.
* Archive entry creation must be idempotent, so a retry after a quota race cannot create duplicates.
* A concurrent upload may temporarily exceed the limit under report-only; this is acceptable and must be visible.
* This ADR states the consistency model; it does not claim precise real-time enforcement.

### 11.9 First-release quota summary

| Behaviour | First release | After DR-08 |
|---|---|---|
| Resolve plan limit | Yes (contract) | Yes |
| Report usage | Yes, if available; nullable | Yes |
| Block archive writes | No | Per Product decision |
| Paid extension | No | Per Product/Finance |
| Second quota table | No | No |
| Quota values in Archive | No | No |

**Decision status:** PA-4 authority is APPROVED (existing record). DR-06, DR-07 are PROPOSED (pending Architecture Team + Product Owner). DR-08 is PROPOSED and MUST BE DECIDED BEFORE PRODUCTION.

## 12. Decision 9 - Retention Architecture

**Chosen (PA-3 product-approved direction + Architecture mechanism): retention is configurable by document type, jurisdiction and school. The mechanism is specified; the values are owned by Product/Legal. Permanent preservation and secure destruction are distinct. Destruction is disabled by default and is not implemented in the first release.**

### 12.1 Design principles

1. The **mechanism** is architecture; the **values** are Product/Legal.
2. No statutory duration is invented or implied.
3. No policy means **preserve indefinitely**, never destroy.
4. Permanent preservation and secure destruction are distinct disposition classes.
5. Destruction is disabled by default and is not implemented in the first release.
6. Every policy match, evaluation, extension, hold and disposition is audited.
7. A policy change must not retroactively destroy records without an explicit, audited migration decision.

### 12.2 Document categories and scope

Retention policies must be selectable by:

* `school_id` (nullable = platform default);
* `document_type` (nullable = all types);
* `jurisdiction` (nullable; required before a `destroy` policy is activated);
* optional `academic_context` filters only if Product requires them (not assumed).

The category axis is data, not a closed code enum. Suggested categories for Product/Legal confirmation are: official academic document, report card / transcript / certificate, class council record, administrative record (not in first release) and operational audit (separate retention class). The ADR does not hard-code this list.

### 12.3 Policy schema (proposed)

**`archive_retention_policies`**

| Column | Notes |
|---|---|
| `id` | Primary key |
| `school_id` | Nullable = platform default |
| `document_type` | Nullable = all types |
| `jurisdiction` | Nullable; required for `destroy` |
| `retention_months` | Nullable = indefinite |
| `disposition` | `preserve` or `destroy` |
| `legal_basis` | Required for `destroy`; text |
| `is_active` | Boolean |
| `effective_from` | Date/time |
| `created_by` | Actor |
| `created_at`, `updated_at` | Audit |

**Precedence (most specific wins):**

1. school + document type
2. school + all types
3. platform + document type
4. platform + all types

If two policies at the same specificity conflict, the most recent `effective_from` wins and the conflict is audited. If no policy matches, `preserve` with `retention_months = null`.

**Clock start (proposed default):** `archive_entries.archived_at`, with an optional `retention_starts_at` override. Publication and generation dates are inputs to policy matching, not the default clock. The clock choice remains subject to Product/Legal approval (DR-09, UQ-02).

**Evaluation triggers:** on archive entry; scheduled periodic evaluation; manual dry-run. Evaluation is idempotent and records policy id, computed due date, outcome and actor.

### 12.4 Legal hold

* `legal_hold` boolean plus `legal_hold_reason`, `placed_by`, `placed_at`, `released_by`, `released_at`.
* A legal hold always wins over retention and destruction.
* Only an authorized role may place or release a hold; both actions are audited.
* Hold release does not automatically destroy; it returns the record to normal evaluation.
* The proposed default is a hold per entry, with an optional school-wide hold if Legal requires it. The final scope is subject to Legal approval (DR-09, DR-11, UQ-06).

### 12.5 Eligibility, destruction authorization and permanent deletion

**Eligibility for archival:** a record is eligible when the lifecycle read returns `RecordLifecycleState::Archived`, the source document status is consistent, and the tenant is resolved. Divergence between lifecycle and document status is an auditable exception, not a silent archive.

**Eligibility for destruction:** a record is eligible only when:

1. a matching policy has `disposition = destroy` and a legal basis;
2. the retention period has elapsed;
3. no legal hold is active;
4. a dry-run has been produced and reviewed;
5. an approval record exists;
6. the operator holds `archive.destroy`;
7. the two-person rule is satisfied if Security requires it;
8. the deletion certificate is generated and audited.

**Destruction authorization:** a workflow, not a flag. The approval record must state who, what scope, why, evidence and expiry, and must enforce separation of duties. A configuration toggle or code comment is not a safeguard.

**Permanent deletion:** the first release performs no physical deletion. A later release may implement it only after DR-10/DR-11 and Product approval. Metadata soft-delete alone is not destruction. Backup copies must not be used to resurrect destroyed records without an approved restore procedure.

### 12.6 Values requiring Product and Legal approval

The following require explicit, recorded approval. **None is set by this ADR.**

| Value / rule | Owner | Why |
|---|---|---|
| Retention duration per document type | Product + Legal | Statutory and policy obligation |
| Jurisdiction applicability | Product + Legal + Privacy | Cross-border and local law |
| Legal basis for destruction | Legal/Compliance | Lawfulness |
| Permanent preservation categories | Product + Legal | Records-management policy |
| Legal-hold authority and release | Legal/Compliance | Litigation/investigation control |
| Destruction approval matrix and two-person rule | Product + Security + Operations + Legal | Safeguard design |
| School-level override rights | Product + Legal | Contractual and legal constraints |
| Offboarding/school-closure behaviour | Product + Legal + Operations | Retention and erasure duties |

**No country-specific retention period is asserted or implied anywhere in this ADR.**

### 12.7 Audit evidence for retention

Every evaluation records: policy id, scope, matched rule, clock start, computed due date, outcome (`preserve`, `due`, `held`, `destroy_approved`, `destroyed`, `error`), actor/system, timestamp and correlation id. Every policy change records old and new values. Every hold records placement/release. Every destruction records a certificate and the approval reference.

## 13. Decision 10 - Audit Architecture

**Chosen (Architecture proposal): classify audit rows before setting retention; add an Archive event catalogue; do not rely on the generic ninety-day cleanup for records or compliance evidence. The seven-year versus ninety-day contradiction is recorded, not silently resolved.**

### 13.1 Existing audit mechanisms (verified)

| Mechanism | Evidence | Classification |
|---|---|---|
| Generic `audit_logs` | `database/migrations/2026_07_17_000070_create_audit_logs_table.php` | **VERIFIED IMPLEMENTED** |
| Generic cleanup of `AuditLog`, `ActivityLog`, `SystemHealth` | `app/Console/Commands/System/SystemCleanupCommand.php:14,23-29` | **VERIFIED IMPLEMENTED** |
| Cleanup scheduled daily with `--days=90` | `bootstrap/app.php:47` | **VERIFIED IMPLEMENTED** |
| Document audit journal | `app/Domains/AcademicCommunication/Infrastructure/Models/DocumentAudit.php`; `2026_08_06_000009_create_document_audits_table.php` | **VERIFIED IMPLEMENTED** |
| Document audit cascades on school/document delete | Same migration | **VERIFIED IMPLEMENTED** (risk carrier) |
| Audit retention documented as minimum seven years | `docs/03_Database/Audit.md:74-79` | **DOCUMENTED INTENT**, not enforced |
| Archive audit events | None | **NOT IMPLEMENTED** |

### 13.2 The contradiction

`docs/03_Database/Audit.md:74-79` states audit logs are immutable with a minimum seven-year retention. The scheduled `system:cleanup --days=90` deletes `audit_logs` older than ninety days. Both cannot be true for the same rows.

**This ADR does not choose a retention period.** It requires the following before archive audit is used as retention evidence:

1. audit rows are classified (operational / security / records / compliance);
2. each class has an owner and a configured duration;
3. records and compliance evidence is either stored in a dedicated append-only stream or explicitly exempted from generic cleanup;
4. the seven-year document claim is corrected or the cleanup is changed, by the owner, with evidence.

Until then, the contradiction remains open (DR-13). The consequence of not deciding is that retention evidence can be deleted after ninety days while the platform claims seven years.

### 13.3 Proposed retention classes

| Class | Examples | Proposed retention owner | Store |
|---|---|---|---|
| `operational` | health checks, routine activity feed | Operations | Existing logs / `system_health` |
| `security` | login, access denial, permission change, super-admin break-glass | Security | `audit_logs` or dedicated security stream |
| `records` | archive entry, retention evaluation, hold, disposition, restoration | Legal/Compliance + Product | Dedicated append-only archive stream |
| `compliance` | destruction certificate, legal-hold placement/release, approval record | Legal/Compliance | Dedicated append-only archive stream |

The durations are not set here. The generic ninety-day cleanup may continue to apply only to classes it is authorized to delete.

### 13.4 Archive event catalogue (proposed)

| Event | Trigger | Minimum payload | Class |
|---|---|---|---|

| `archive.downloaded` | Authorized download succeeds | school, entry, actor, IP/UA, checksum verified, outcome | records/security |
| `archive.access_denied` | Wrong tenant, missing permission, missing object or path rejection | school, requested id/path hash, actor, reason, IP/UA | security |
| `archive.metadata_modified` | Archive metadata or provenance changes | school, entry, actor, old/new values | records |
| `archive.retention_policy_modified` | Policy created, updated or deactivated | school/default, policy, actor, old/new values | compliance |
| `archive.archived` | Entry created from an archived lifecycle record | school, entry, lifecycle id, source identity | records |
| `archive.restored` | Entry or source restored under an approved procedure | school, entry, actor, reason, approval | records |
| `archive.deletion_requested` | Destruction workflow starts | school, entry, requester, reason, approval | compliance |
| `archive.destroyed` | Physical or logical destruction completes | school, entry, operator, certificate id | compliance |
| `archive.quota_evaluated` | Quota projection read/evaluated | school, plan, limit, used, mode, outcome | records |
| `archive.quota_exceeded` | A quota threshold or limit is hit | school, plan, usage, threshold, action taken | records/security |
| `archive.integrity_failed` | Checksum mismatch or missing object | school, entry, expected/actual, action | security |
| `archive.admin_action` | Any privileged archive administration | school, actor, action, scope, result | security |
| `archive.export_requested` / `archive.export_completed` | Package request and delivery (deferred) | school, requester, manifest hash, expiry | compliance |

**Rules:** append-only; actor + timestamp + school + correlation id; no silent success on failure; no event may contain grades, content or unnecessary personal data; denial events must not leak whether another tenant's object exists.

### 13.5 Store strategy (proposed default)

Options:

1. A dedicated `archive_events` append-only table with its own retention and no generic cleanup. **Proposed default.**
2. `audit_logs` with a `retention_class` column and a cleanup exemption. Simpler, but requires modifying existing cleanup behaviour and risks accidental deletion.
3. Extending `document_audits`. Attractive because it is already append-only, but it is owned by SPR-012 and cascades on document deletion; using it for retention evidence couples Archive to a mutable source lifecycle. **Not recommended without an ownership change.**

This ADR does not modify any audit table or cleanup job. The store choice is DR-12; the retention-class decision is DR-13.

**Decision status:** DR-12 and DR-13 are PROPOSED (pending Architecture Team + Security Lead + Legal/Compliance).

### 14.2 Permission model (proposed)

| Permission | Capability | Notes |
|---|---|---|
| `archive.view` | List and read archive metadata | School-scoped |
| `archive.download` | Download an authorized object | Separate from view if Security prefers |
| `archive.manage` | Create/reconcile archive entries, manage metadata | No source mutation |
| `archive.retention.manage` | Create/update retention policies | Requires compliance training/role |
| `archive.export` | Request/download packages (deferred) | High-risk capability |
| `archive.destroy` | Approve/execute destruction (deferred) | Highest-risk; two-person rule |

Add an `Archive` case to `PermissionGroup` and seed permissions through the existing permission mechanism. Do not reuse `document.*`. Policies must deny `delete`, `restore` and `forceDelete` except through the explicit destruction workflow, which is off in the first release.

### 14.3 Download authorization pipeline (proposed)

1. Resolve tenant from the authenticated request.
2. Authorize `archive.view` / `archive.download` for the school.
3. Load the archive entry by `school_id` + id (never by path).
4. Validate `disk` against the allow-list and canonicalize `path`.
5. Verify the object exists and the checksum matches.
6. Stream with `Content-Disposition: attachment`, a safe content type and no inline rendering.
7. Audit success or failure.
8. Return a uniform 404 for wrong tenant, missing object or unauthorized id (no existence leak).
9. Apply rate limiting. If a short-lived signed URL is used later, authorization must precede issuance, the URL must expire quickly and the issuance must be audited.

### 14.4 Integrity

* SHA-256 at archive entry; compare with the source `generated_files.checksum` when available.
* Verify before every download.
* Scheduled integrity job across active entries; quarantine on mismatch.
* Audit `archive.integrity_failed` and surface it to operations.
* Never silently serve a different file or a stale version.

### 14.5 Encryption at rest and key management

**Truthful current state:** no application-level encryption at rest is implemented for local archive objects. `config/database.php:113` has `// 'encrypt' => ...` commented. No `Crypt` / `Encrypter` / `openssl_encrypt` usage was found in application code. Host or volume encryption is **UNVERIFIED**.

**Decision required (DR-16):** state whether the first release:

* (a) requires application-level envelope encryption for archive objects, with keys managed outside the repository; or
* (b) accepts the risk with documented infrastructure controls and a production gate; or
* (c) requires host/volume encryption evidenced by Operations.

**Do not claim encryption until the chosen control is evidenced.** Cloud key management and rotation (platform-held versus school-held, tenant key separation) remain deferred and block cloud activation (DR-20).

### 14.6 Super-admin break-glass

The platform has a super-admin bypass pattern. Archive must define whether super-admin can read or export any school's archive, under what approval, and with what audit. Silent cross-tenant access is prohibited. The proposed default is explicit break-glass with a reason, a second approval where feasible, and an audited `archive.admin_action` event (DR-26). No approval exists today.

### 14.7 Auditability

Authorization failures, integrity failures, downloads, metadata changes, retention evaluation and any privileged administration are auditable. Denial events must not reveal whether another tenant's object exists.

**Decision status:** DR-14, DR-15, DR-16, DR-26 are PROPOSED (pending Security Lead + Architecture Team). DR-17 is PROPOSED and MUST BE DECIDED BEFORE PRODUCTION.

## 15. Decision 12 - Tenant Isolation and Private File Ownership

**Chosen (Architecture proposal): tenant isolation is enforced in authorization AND in the storage key/path structure. Path `school_id` alone is never authorization. Archived official documents use private storage by default.**

* **Storage structure:** archived objects live under a per-school prefix, `archive/{school_id}/{...}`, mirroring the existing `documents/{school_id}/...` convention. The tenant disk suffix (`filesystem.suffix_base` + tenant id) remains the primary tenancy boundary on `local` / `public`.
* **Private by default:** archived official documents must never be written to the `public` disk or served from a public URL. The private `local` disk (`storage_path('app/private')`) is the first-release home.
* **Authorization:** every archive read/download is re-checked against the resolved tenant and principal through the archive domain's authorization surface. No read trusts only the `school_id` embedded in the path.
* **Cross-tenant rule:** no archive operation may address another tenant's prefix or tenant disk, and no shared object contains two tenants' data without an explicit per-tenant access-control layer. For cloud, that layer is deferred and is a mandatory activation condition (Decision 13).
* **Tenant deletion:** archive metadata must not cascade blindly on tenant deletion. Offboarding behaviour is a retention decision (DR-09, DR-10, UQ-05). The `generated_files` cascade is evidence of the risk, not a pattern to copy.
* This invariant holds for local storage now and is the mandatory precondition for cloud activation.

**Decision status:** PROPOSED (DR-05, DR-15), pending Architecture Team + Security Lead. The local-first tenancy pattern is VERIFIED IMPLEMENTED; archive-specific enforcement is NOT IMPLEMENTED.

## 17. Decision 14 - Downloadable School Archive Packages

**Chosen (PA-5 product-approved scope + Architecture boundary): downloadable school archive exports are in architectural scope but NOT mandatory for the first release.**

* **In scope now (boundary and security design):** define the capability - tenant-scoped, request-authorized, auditable, completeness and integrity checked, controlled access, with expiry and cleanup and safe failure behavior. The security boundary is fixed at this ADR level:
  * **Authorization:** only principals granted the archive-export capability may request a package; a request carries an explicit actor, reason and time window.
  * **Strict tenant isolation:** a package contains exactly one school's records; cross-tenant inclusion is prohibited.
  * **Auditability:** every request, generation and delivery is an auditable event.
  * **Integrity and completeness:** packages carry a manifest with verification hashes; incompleteness fails loudly, never silently.
  * **Expiry and cleanup:** packages are temporary artifacts with an expiry and are cleaned up; delivery is not a defensible permanent store.
  * **Safe failure:** a failed package generation yields no partial "success" artifact and is retryable.
* **Out of scope until a later release:** package generation/download routes, UI, jobs, persistence, formats, contents listing, max sizes, retention/expiry values, permission surface and delivery mechanism. These are deferred (DR-24).
* First release = local archive + retention mechanism + quota read contract; packages add no first-release dependency.

**Decision status:** PA-5 scope is APPROVED (existing record). DR-24 (package specifics) is **DEFERRED** (MAY BE DEFERRED). DR-14 covers the `archive.export` permission when packages are later approved.

## 18. Decision 15 - Backup versus Archive Separation

**Chosen (Architecture proposal): archive/retention is distinct from operational backup. Archived objects and metadata remain in backup scope, and a restore drill is required before production.**

* Backup (scope, schedule, encryption, 30d/12w/12m retention, RTO/RPO) remains the operations-owned recovery pipeline (`docs/08_Deployment/Backups.md`). Archive is records management: authoritative, long-term, retention-policy driven, with its own provenance and future export.
* SPR-017 creates no backup schedule, no snapshot machinery and no recovery SLO; it must not shadow the backup team's RTO/RPO obligations.
* Archived documents **remain covered by operational backup** (archive is not a removal-from-backup signal), but backup retention is **not** the archival retention mechanism.
* **Current implementation is not the documented intent.** `BackupService::executeBackup()` writes a schema-only placeholder, does not copy files and does not encrypt. `restore()` only dispatches an event. `system:backup` is not scheduled. The documented PostgreSQL/MySQL conflict is also recorded. Archive backup coverage, encryption and restore are **NOT IMPLEMENTED / UNVERIFIED**.
* Before production: archive paths and metadata must be added to backup scope; backup encryption must be evidenced; a restore drill including at least one archived object must be performed and recorded; the documented RTO/RPO must be measured or restated as targets.

**Decision status:** DR-19 (separation invariant) is PROPOSED and MUST DECIDE BEFORE ADR ACCEPTANCE. DR-18 (backup/recovery including archive objects) is PROPOSED and MUST BE DECIDED BEFORE PRODUCTION.

## 19. Security Invariants

* **S1 - No cross-tenant archive access:** every archive operation resolves a tenant and never addresses another tenant's objects. `school_id` in a path is never authorization by itself.
* **S2 - Archive never mutates source records:** the archive domain reads through contracts and writes only its own provenance, retention and audit metadata.
* **S3 - No unauthorized permanent deletion:** automatic secure destruction is disabled; deletion only via an authorized, auditable, operator-initiated path. The first release performs no physical deletion.
* **S4 - Integrity checkable:** archived objects and future packages expose verifiable digests/manifests. Silent partial data is impossible by design. A checksum mismatch fails closed.
* **S5 - Audit:** archive entry, access, download, retention evaluation, hold, disposition and any package request/generation are auditable events.
* **S6 - No cloud capability, no SLO claim:** nothing in SPR-017 asserts cloud provision, durability, availability or cost that is not gated and approved.
* **S7 - Legacy exclusion:** nothing in SPR-017 reads or writes `app/Models/GeneratedDocument`, `app/Models/DocumentTemplate`, `app/Services/DocumentGenerationService`, legacy `app/Domains/Document` or legacy DocumentCenter / `pdf_enable_qr_code`.
* **S8 - Private by default:** archived official documents are stored on the private disk and served only through an authorized streaming path. No public URL, no inline rendering, no directory listing.
* **S9 - Truthful controls:** no encryption, backup, restore, integrity or audit capability may be claimed unless repository evidence or a signed operational record demonstrates it.
* **S10 - Denial does not leak:** unauthorized, wrong-tenant and missing-object responses are uniform and do not reveal another tenant's existence.
* **S11 - Privileged access is intentional:** super-admin or break-glass access is explicit, approved and audited, never a silent bypass.

## 28. Consequences

### 28.1 Positive

* Local-first launch is possible without any cloud dependency, preserving the current no-cloud-infrastructure posture.
* Retention is a genuinely configurable mechanism per document type, jurisdiction and school, ready for legal values without a code change.
* A single quota authority keeps plan semantics authoritative and avoids a second billing/quota story.
* The provider-neutral storage port keeps provider choice open and activation reversible; no lock-in decision is forced today.
* The SPR-014 boundary is respected: archive is additive and contract-only.
* Packages are designed as a secure, auditable, tenant-isolated capability from the start, even though deferred.
* The audit, encryption and backup sections now state the actual repository position instead of implying controls that do not exist.

### 28.2 Negative / accepted consequences

* Cloud capacity (durability, availability, cost, key rotation) is **not** available at first release - an accepted consequence of local-first.
* Retention values and destruction authorization remain unresolved by design; the mechanism cannot enforce durations Product/Legal has not approved.
* No metering and no quota hard enforcement exist; storage growth is reported, not blocked.
* A local-disk archive is operationally distinct from a resilient archive; this is disclosed, not masked.
* The PA-1 phase-placement correction means SPR-017 is strategic (Phase 9); near-term sprint planners must not treat it as an ordinary Phase 3 deliverable.
* The revised decision surface is larger than version 1.0. That is deliberate: the missing decisions were being pushed into implementation.

### 28.3 Residual risks not removed by this revision

The risks in section 26 remain live. The most important are: the audit-retention contradiction (RR-05), the unproven encryption posture (RR-07), cross-tenant exposure if the download path is built without the specified controls (RR-08), the absent backup/restore evidence (RR-13/RR-19), and the SPR-014 interlock (RR-01). This revision specifies controls and gates; it does not implement or approve them.

## 29. Rejected Alternatives

1. **Extending `RecordsLifecycle` in place to host archive semantics** - rejected: violates SPR-014's thin-lifecycle scope and risks duplicate lifecycle ownership. Archive is a new bounded context.
2. **Platform service outside `App\Domains`** - rejected: weakens DDD/contract discipline and the `DEPENDENCY_MAP.md` shape.
3. **A dedicated quota store in Archive** - rejected: duplicates the plan authority; `plans.storage_limit` remains the single source of truth (PA-4).
4. **Cloud-first / cloud required for first release** - rejected (PA-2): no cloud dependency, no unsupported SLO, decoupled seam.
5. **Hard-coding a single cloud vendor SDK as the only storage path** - rejected: creates lock-in and breaks the provider-agnostic activation gate.
6. **Mandatory S3-compatible abstraction** - rejected: no provider or protocol has been approved; a provider-neutral port with a local adapter is sufficient and reversible.
7. **Auto-destruction enabled by default under retention policies** - rejected: no legal values, no authorization/safeguard design; destruction stays off until DR-10/DR-11 close.
8. **Statutory retention defaults invented by architecture** - rejected: legal/regulatory research is a separate task; architecture does not set law.
9. **`school_id`-in-path as sufficient isolation for archive reads** - rejected: every read is re-authorized; a path alone is never a capability.
10. **Packages mandatory in first release** - rejected (PA-5): boundary/security defined now, implementation deferred; no format/contents/size commitments.
11. **Reviving legacy `GeneratedDocument` / `DocumentTemplate` / `DocumentGenerationService` / `app/Domains/Document`** - rejected: fixed constraint (LG1), mirrors ADR-021/022 L1-L3.
12. **Reusing the backup pipeline as the retention mechanism** - rejected: backup is operational recovery; retention is records management.
13. **Using `document_audits` as the archive retention-evidence store** - rejected without an ownership change: it cascades with source document deletion, so it cannot prove retention after a source record is deleted.
14. **Relying on the generic ninety-day cleanup for archive evidence** - rejected: it contradicts the documented minimum seven-year audit retention and deletes records management evidence.
15. **Serving archived files from the `public` disk or a permanent public URL** - rejected: official records require private storage and authorized streaming.
16. **Treating `plans.storage_limit` as an implemented quota because a column exists** - rejected: a string column with no parser, resolver, metering or enforcement is not a quota mechanism.
17. **Treating passing tests as SPR-014 closure** - rejected: the project Definition of Done also requires review approval, staging deployment and a recorded closure decision.
18. **A generic project waiver as an automatic substitute for staging evidence** - rejected: a waiver must be explicit, owner-signed, scoped, dated and risk-bearing.

## 30. Implementation Constraints

Contract obligations placed on the future SPR-017 implementation:

* **C1 - Contract-only reads:** Archive Domain/Application must not import source-domain infrastructure models. It depends on the named read contracts.
* **C2 - No lifecycle writes:** Archive never calls `RecordLifecycleService` to mutate state; it only reads through `ArchivedLifecycleReadContract`.
* **C3 - Tenancy discipline:** per-school prefixes plus authorization on every read; path is not authorization.
* **C4 - Storage port:** Domain/Application depend on `StoragePort`. A local adapter is first; an S3-compatible adapter is optional and gated.
* **C5 - Retention evaluation is value-driven:** durations and dispositions come from the policy store, never hard-coded. Unconfigured means preserve indefinitely, never destroy.
* **C6 - Quota integration reads the plan authority through `StorageQuotaContract`:** no second quota table and no quota values stored in Archive.
* **C7 - No package machinery in first release:** no package routes, UI, jobs or persistence until DR-24 closes.
* **C8 - Audit:** archive entry, access, retention, hold and disposition events are appended with actor, timestamp, school and correlation id.
* **C9 - No cloud config/credentials/SDK/dependency:** strictly local until the Decision 13 gate is fully approved.
* **C10 - APP domain name `App\Domains\Archive`** unless a later architectural review renames it before implementation. Rename before code, not after.
* **C11 - Private storage only:** archived official documents use the private disk. No public disk and no public URL.
* **C12 - Verify before serving:** checksum verification before download; fail closed and audit on mismatch.
* **C13 - Idempotent entry:** `(school_id, source_domain, source_type, source_id, source_version)` is unique. Retries must not duplicate entries.
* **C14 - Truthful capability claims:** code comments, docs and UI must not claim encryption, backup, restore or durability that the implementation does not provide.
* **C15 - No silent deletion:** first release performs no physical deletion. Metadata soft-delete is not destruction.

## 32. Testing Requirements

During SPR-017 implementation (tests are out of scope for this decision phase; this ADR is decision-only):

* **Tenant isolation:** school A cannot read, list, request or receive any archive artifact of school B. A path `school_id` misdirection is rejected by authorization. Cross-tenant negative tests are mandatory.
* **Trigger correctness:** only `archived` lifecycle records enter the archive; `registered` and `published` records never do.
* **Dual-state divergence:** when document status and lifecycle state disagree, the entry is not created silently; an audited exception is produced.
* **Retention matrix:** per-document-type, per-jurisdiction and per-school durations and dispositions evaluate as configured. Unconfigured scopes default to no destruction and no period.
* **Destruction safety:** with auto-destruction disabled, no test can produce deletion of an archived record without an authorized operator action, dry-run and approval record.
* **Quota authority:** quota reads use `StorageQuotaContract`; no second quota table or authority exists. Invalid units fail closed; no-subscription is reported, not treated as unlimited.

* **Download security:** authorization precedes object lookup; uniform 404 for wrong tenant; attachment disposition; rate limiting; audit on success and failure.
* **Architecture tests:** no import of `RecordLifecycle`, `AcademicDocument`, `GeneratedFile`, legacy document classes, or `Storage::disk()` in Archive Domain/Application.
* **Idempotency:** repeated archive-entry creation for the same source identity yields one row.
* **Backup separation:** SPR-017 introduces no backup schedule or snapshot machinery.
* **Legacy exclusion:** architecture tests assert no import of legacy document classes.

Full-suite requirement, PHPStan and Pint gates apply at implementation time per the project's Definition of Done. No test was run for this documentation revision.

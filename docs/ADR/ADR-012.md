# ADR-012
# Academic Communication Engine Architecture

**Status:** Accepted

**Date:** 2026-08-04

**Decision Makers:**

- Solution Architect
- Backend Architect
- Academic / Domain Expert

---

# Context

A school produces a steady stream of official academic documents: report
cards, council minutes, summaries for parents / teachers / students, academic
statistics, school chronicles, transcripts, certificates, enrollment
confirmations and official letters. Each business engine (Assessment,
Gradebook, Attendance, Class Council, Guardian, Staff) knows its own data but
none owns "the document": history, numbering, versioning, approval, visibility
and delivery were scattered across engines or missing entirely.

NexusSchool needs a **single publication layer** so that:

- every official document gets a **permanent identity** that survives
  corrections;
- a published document is **immutable** — a correction is a new version, never
  an overwrite;
- every transition is **authorized** (capability-based), **school-scoped** and
  **audited**;
- what each audience sees is controlled by a **visibility policy** (a parent
  must never see council decisions; a director may see everything);
- documents reach their audience through **pluggable channels** (portals, PDF
  export today; email / SMS / push tomorrow).

SPR-001/002 (Academic), SPR-006 (Staff), SPR-009 (Assessment) and the later
domain sprints established the DDD + Actions structure, the contract/adapter
boundary and the tenant-isolation conventions that this decision must follow.

---

# Problem Statement

How should NexusSchool model official academic documents and their publication
so that:

- the engine is the **only** place documents are generated and published;
- **versions are immutable** and the document identity is **permanent**;
- **visibility is policy-driven** and can be configured per school;
- **delivery is channel-pluggable** and traceable per recipient;
- every query is **school-scoped** and every action **capability-gated**;
- the engine never imports a foreign engine's model?

The model must not leak transition logic into the Eloquent model, must not let
the Filament layer bypass the application actions, and must not couple the
engine to any business engine's schema.

---

# Decision

Nexus adopts a **single AcademicDocument aggregate root** with immutable
version rows, policy-driven visibility, a notification-based publication
pipeline, and **contracts instead of foreign-model imports**.

```text
AcademicDocument (aggregate root, permanent number, forward-only status)
   ├─ AcademicDocumentVersion (immutable, version_no, content snapshot)
   │     └─ GeneratedFile (official PDF; exactly one is_current per document)
   ├─ DocumentApproval (pending -> approved | rejected)
   ├─ DocumentSignature
   ├─ DocumentRecipient (director | secretary | teacher | parent | student)
   ├─ PublicationRecord (per document x channel x recipient)
   │     └─ PublicationDeliveryAttempt (one per delivery)
   └─ DocumentAudit (append-only journal)

DocumentStatus: draft -> generated -> reviewed -> approved -> published -> archived
                (approval skipped when the policy requires none)
```

- The `AcademicDocument` model is the aggregate root and holds **no transition
  logic**. All invariants live in **application Actions**, invoked only through
  the `AcademicCommunicationService` facade.
- **Permanent identity:** `{platform}-{year}-{school}-{type}-{seq}`
  (e.g. `NS-2027-SCH001-RC-000000145`). Sequence is count-based per school and
  per document type; regeneration keeps the identity unchanged.
- **Immutability:** `DocumentStatus::isImmutable()` is true for published and
  archived. Corrections go through `RegenerateDocumentAction`, which creates a
  new immutable version, re-renders the official file and flips
  `GeneratedFile.is_current` for **all** of the document's files. Published
  records are never mutated; a re-delivery creates a new `PublicationRecord`.
- **Business data enters only through Domain Contracts** (`AssessmentContract`,
  `GradebookContract`, `AttendanceContract`, `ClassCouncilContract`,
  `GuardianContract`, `StaffContract`, `AcademicFrameworkContract`,
  `AcademicPoliciesContract`, `StudentIdentityContract`, `SchoolContract`),
  implemented by Infrastructure adapters and bound in the provider — the only
  place the engine sees foreign models.
- **Visibility is policy-driven:** a `PublicationPolicy` carries a
  `VisibilityPolicy` mapping every `VisibilityScope`
  (director / secretary / teacher / parent / student / inspector) to the
  document sections it may see. Parents and students are always self-scoped.
- **Publication:** a `PublicationRecord` per (document, channel, recipient);
  delivery requires **at least one completed** channel or
  `DocumentPublicationFailedException` is thrown. Channels implement
  `PublicationChannelContract` and are declared in
  `config/nexus-academic-communication.php` (5 delivered: internal / parent /
  teacher / student portal + pdf_export; `email`, `sms`, `push_notification`
  declared but un-delivered — the dispatcher refuses them via
  `DocumentChannel::isImplemented()`).
- **Authorization** is centralized in `HandlesDocumentAuthorization` with 7
  capabilities (`document.view/generate/review/approve/publish/archive/
  template.manage`), capability-based (never role-based) with the
  `super_admin` bypass and school scoping on every check.
- Deletion is disabled on the aggregate; history is preserved via the
  append-only `document_audits` journal.

# Alternatives Considered

## Option 1

Each business engine owns its documents (report cards in Assessment, minutes in
Class Council, …).

### Advantages

- Each document lives next to its source data.

### Disadvantages

- Numbering, versioning, approval, visibility and audit logic is duplicated
  per engine and drifts.
- No single source of truth for "who published what to whom".
- Immutability and permanent identity cannot be enforced uniformly.
- Adding a channel (e.g. email) means touching every engine.

---

## Option 2

A generic document store with no aggregate semantics (blob + tags).

### Advantages

- Simple to write and to read.

### Disadvantages

- No lifecycle: status, approval, versioning and visibility rules leak into
  every caller.
- No permanent numbering, no immutability guarantees.
- Recipient scoping and delivery traceability are impossible to enforce.

---

## Option 3 (Chosen)

Single `AcademicDocument` aggregate + immutable versions + contracts.

### Advantages

- One canonical engine for generation and publication.
- Permanent identity + provable immutability (published / archived).
- Policy-driven visibility and channel-pluggable delivery.
- Cross-engine data arrives through contracts — the domain never imports a
  foreign model, keeping the dependency graph acyclic.
- Tenant isolation applied on every query; capability-based authorization.

### Disadvantages

- More tables and more moving parts than a blob store.
- Business data must be adapted (contract → adapter) before rendering.
- New channels and document types require config + an adapter or a template.

---

# Consequences

All official document flows in NexusSchool now go through
`AcademicCommunicationService`.

This concerns:

- Filament resources (AcademicDocument, AcademicDocumentTemplate,
  PublicationChannel, PublicationPolicy) under "Communication académique"
- Authorization and permission definitions (`document.*`)
- Future sprints that need to publish documents (Report Card, Class Council,
  Attendance, Transcript) — they will dispatch through the engine's contracts
  and generators rather than render their own documents.

New document features must preserve the forward-only lifecycle, version
immutability and the contract boundary.

---

# Positive Impacts

- Single, audited, tenant-isolated publication layer.
- Permanent document identity; published records can never be overwritten.
- Capability-based authorization with no role coupling.
- Channel and visibility configuration per school without code changes.
- Contract boundary keeps the engine decoupled from every business engine.

---

# Negative Impacts

- Larger schema (12 migrations) and more code than per-engine documents.
- Business data must cross a contract/adapter boundary before rendering.
- Delivering email / SMS / push requires implementing a channel driver.

# Implementation Notes

Implemented under `app/Domains/AcademicCommunication`:

- `Infrastructure/Models/AcademicDocument` — aggregate root (number, status,
  origin, scopes, version helpers).
- `Application/Actions/*` — 12 explicit actions (generate + 6 generators,
  review, approve, publish, archive, regenerate).
- `Application/Services/AcademicCommunicationService` — the only public entry
  point; `DocumentNumberGenerator`, `DocumentContentComposer`,
  `PublicationRecipientResolver`, `PublicationDispatcher`.
- `Domain/Enums/DocumentStatus` / `DocumentType` / `DocumentChannel` /
  `VisibilityScope` / `ApprovalStatus` / `PublicationStatus` — state machines
  and catalogs.
- `Domain/Contracts/*` + `Infrastructure/Contracts/*` — the cross-domain
  boundary, bound to adapters in `AcademicCommunicationServiceProvider`.
- `Infrastructure/Renderers/HtmlDocumentRenderer` — renders the official
  content (swappable via the `renderer` config).
- `Infrastructure/Channels/*` — 5 delivered channel drivers.
- `Infrastructure/Policies/*` + `Domain/Traits/HandlesDocumentAuthorization` —
  capability-based authorization.
- `Domain/Events/*` + `Infrastructure/Listeners/AcademicCommunicationAuditLogger`
  — audit + journal.

Schema: 12 migrations (`2026_08_06_000001` → `000012`).

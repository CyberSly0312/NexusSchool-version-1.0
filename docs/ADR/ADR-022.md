# ADR-022: Academic Document Verification Architecture and Governance (SPR-016)

## Status

Accepted

## Date

2026-09-07

---

## Context

SPR-016 (Identity & Verification Engine) requires an architecture decision before
any implementation may begin. SPR-016's purpose is the **public verification of
academic documents** produced by SPR-015 (Certificate & Transcript Engine) through
the SPR-012 (Academic Communication Engine) substrate.

The SPR-016 Phase 1 discovery report (2026-09-07) validated the following
substrate facts, which this ADR relies upon:

* **Document identity is sequential and enumerable.** `DocumentNumber` follows the
  format `NS-2027-SCH001-RC-000000145`; the number is issued per
  `(school_id, document_type, academic_year)` through `DocumentNumberGenerator` and
  is deterministic, sequential, and carries no checksum. It is a human-facing
  identifier, not a secret and not a capability.
* **The document aggregate is versioned and immutable.** `AcademicDocument`
  (aggregate root; row-level `school_id` via `HasSchoolId`) starts life at status
  `Generated` and carries `content_version`; every change creates an
  `AcademicDocumentVersion` with `content_hash` (SHA-256 of the JSON content),
  `is_published` and `published_at`. Rendering produces a `GeneratedFile` with a
  SHA-256 `checksum` and an `is_current` flag; re-rendering marks the previous file
  historical instead of overwriting it.
* **Publication is a delivery record, not an identity.** `PublicationRecord`
  records one delivery attempt per channel/recipient, is `SoftDeletes`-able, and is
  explicitly not authoritative for verification truth.
* **`DocumentStatus`** today expresses `Draft`, `Generated`, ... via
  `AcademicDocument`/`AcademicDocumentVersion`. There is **no revocation concept**
  for documents anywhere in the codebase (revocation semantics exist only for API
  tokens, OAuth tokens, roles and guardian pickup).
* **Templates already carry verification affordances without any machinery:**
  `qr_code_enabled` and `verification_code_enabled` columns exist on
  `academic_document_templates`; `HtmlDocumentRenderer` prints
  "Code de vérification : {{ document_number }}" when enabled and receives an
  unused `qrCodeEnabled` flag. No QR library is present in `composer.json`
  (only `dompdf`, `spatie/laravel-pdf`).
* **No verification route exists.** `web.php` (welcome only), `routes/tenant.php`
  (empty), `api.php` (v1 `oauth/token` public route throttled `10,1` plus protected
  API-token routes).
* **Tenancy is per-school databases** (stancl/tenancy; `tenant_model=School`,
  UUID `school_id`, `DatabaseTenancyBootstrapper`), with
  `TenancyServiceProvider` mounting tenancy middleware at highest priority.
  `routes/tenant.php` is empty — the public verification surface would be a
  **central/global** route, not a tenant route.
* **SPR-015 produces verification-ready documents.** `CompletionRequest` /
  `CompletionRequestEntry` materialize `academic_document_id`,
  `academic_document_number` and `academic_document_type` only; the
  `HandlesCertificateAndTranscriptAuthorization` trait explicitly reserves
  verification capabilities for SPR-016.
* **Legacy system** (`app/Models/GeneratedDocument`, `app/Models/DocumentTemplate`,
  `app/Services/DocumentGenerationService`, legacy `app/Domains/Document`,
  legacy DocumentCenter) is deprecated and must not be revived or reused.
* **ADR-001 is currently an empty file (0 bytes).** This ADR does not depend on its
  content; a governance follow-up to restore or deprecate ADR-001 is recorded in
  `SESSION_HANDOFF.md` (2026-09-07).
* **ADR-021** (Academic Communication, Interaction Design, 2026-09-05) reserves
  verifier capabilities for SPR-016; the six decisions recorded there remain valid.

Decision status at the end of discovery: **NEEDS ARCHITECTURAL DECISION**. This ADR
resolves that.

## Problem Statement

Before implementing SPR-016 the architecture must be decided for:

1. Whether the verification surface is public and who is authorised to call it.
2. The canonical verification identifier and its relationship to the document
   number, URLs, QR payloads and integrity hashes — including whether the document
   number may become a secret.
3. What a public verification response may reveal (disclosure/privacy levels).
4. Whether SPR-016 introduces formal revocation and what "replaced/reor revoked"
   semantically means.
5. The QR architecture — what the QR payload is and who owns its rendering.
6. Tenant resolution of a verification request, guaranteeing school A can never
   fetch school B's documents.
7. Verification semantics across the document lifecycle (unpublished vs published
   vs archived vs revoked vs replaced).
8. Where the verification identity lives over time (aggregate, version,
   publication record, or a dedicated identity).

This ADR is a **decision-only artifact**: no code, no models, no migrations, no
controllers, no routes, no services, no UI. Implementation is deferred to the
SPR-016 implementation phase and must remain within the constraints recorded below.

---

## Decision Summary

SPR-016 operates a **central, public, unauthenticated verification endpoint** based
on a **random opaque verification token** that belongs to the **AcademicDocument
aggregate**, is generated once at document generation, is globally unique and is
stored **SHA-256-hashed**. Verification responses default to a **minimal
disclosure profile (LEVEL 2)** and never expose grades, personal data,
internal identifiers or document content. SPR-016 introduces **formal REVOKED**
and **REPLACED** lifecycle semantics. QR payloads contain **only a verification URL
carrying the opaque token**; QR *rendering* remains the responsibility of the
SPR-012 rendering substrate. Tenant resolution is by central endpoint + opaque
token — never by school code + document number. The document number remains a
non-secret display identifier.

---

## Decision 1 — Public Verification Surface

**Chosen: A — public, unauthenticated verification endpoint.**

External verifiers — employers, universities/other schools, government bodies,
admissions offices, examiners and parents — are **not NexusSchool users**. They
cannot hold platform credentials; a surface gated behind authentication or a school
portal would be unusable by exactly the audience verification exists for. The
purpose of the surface is to let a third party confirm that a physical/academic
document they hold was officially issued.

Consequences and boundaries of choosing A:

* The endpoint is **central** (platform-level), not per-school: a verifier holding
  a document from an unknown school must not need to guess the school's domain.
* Endpoint responsibility: SPR-016 owns the controller/route, the verification
  read-model/contract, rate limiting, abuse protection and audit.
* **Rate limiting**: per-IP throttling at the HTTP layer plus per-token lookup
  limits; public route throttling mirrors the existing `oauth/token` precedent
  (`throttle:10,1`) as a baseline and must be stricter for bulk probing.
* **Abuse protection**: identical cost and timing for valid and invalid lookups;
  no oracle distinguishing "no such token", "unpublished document" or
  "revoked document" beyond the semantic verdicts defined in Decision 3 and 7;
  no redirect or error body that leaks tenant existence.
* **Info-disclosure boundaries**: defined exhaustively in Decision 3; a verifier
  may only learn what the document's verification policy permits, regardless of
  who makes the request.
* **Tenant resolution**: defined in Decision 6 — the endpoint resolves a token to
  exactly one tenant and never exposes tenant enumeration.
* **Invalid/unknown token behavior**: a uniform, non-revealing "no public record"
  response. No distinction that an unpublished document exists.

Authenticated surfaces (management, administrative lookup, portal visibility) are
out of scope of this decision and remain governed by the existing visibility and
authorization machinery.

## Decision 2 — Verification Identity / Token

**Chosen: B — a random opaque verification token as the single canonical public
verification identity.**

### Identity taxonomy (must never be conflated)

| Concept | Example | Role | Secret? |
| --- | --- | --- | --- |
| Internal document identity | `academic_documents.id`, `academic_documents.uuid` | persistence | yes (internal) |
| Document number | `NS-2027-SCH001-RC-000000145` | human-facing display; sequential, enumerable | **no** |
| Verification identifier | opaque token | public verification capability | yes (bearer) |
| QR payload | verification URL + token | encoded presentation of the verification identifier | yes (same bearer) |
| Verification URL | `https://verify…/v/{token}` | machine entry point to verification | yes (same bearer) |
| Cryptographic integrity hash | `content_hash`, `GeneratedFile.checksum` | tamper evidence of content, not identity | no |

### Token properties

* **Generated once** alongside the first document version at generation time, bound
  to the AcademicDocument aggregate (see Decision 8).
* **Random**: drawn from a CSPRNG; base64url-encoded; ≥ 18 bytes (≥ 144 bits) of
  entropy. Collisions effectively impossible at platform scale.
* **Permanent**: survives regeneration of files, replacement, archival and
  revocation. Re-generation is **not** performed in normal operations; if a token is
  suspected compromised, a new document is generated — never a rewritten token.
* **Non-derivable**: cannot be computed from the document number, dates, ids, or
  any enumeration.
* **Stored hashed**: only the SHA-256 of the token is persisted for lookup; the
  plaintext token is shown to the issuing school once at generation and travels only
  inside signatures/QR/printed representation. This matches the platform's existing
  bearer-token hashing precedent.
* **Unique globally** across all tenants — uniqueness is not per-school.
* **Manual entry supported**: the token is short enough to type; the QR is an
  acceleration, not a requirement (see Decision 5).

### Document number

The document number **must never become a secret, a capability, or the public
verification secret**. It is permanently non-confidential: sequential, predictable,
shown on the document itself, and printed today by the renderer as the
"Code de vérification". Making it the verifier's capability would let any holder of
the number (which is deliberately public) fetch the record and would allow
enumerable scanning. Its persistence as a public display plus the opaque token as
the actual capability is the core of the non-enumerability decision.

## Decision 3 — Verification Response / Privacy

**Chosen: default LEVEL 2 — authenticity verdict + type + publication status +
identity-confirming metadata, nothing more.**

### Disclosure levels

| Level | Content | Availability |
| --- | --- | --- |
| LEVEL 0 | "No public record" — uniform, non-revealing failure | invalid/unknown token, unpublished document |
| LEVEL 1 | Authenticity + document type + publication status | opt-in restricted documents |
| **LEVEL 2 (default)** | LEVEL 1 + document number + issuance (generation) date + holder's full name — **only for student-scoped documents, only the person the document is issued to/by** | default for verifiable documents |
| LEVEL 3 | Full content / transcript / grades / personal data | **NEVER** on the public surface |

### Never exposed by the public surface

Grades, transcripts, subject results, date of birth, addresses, telephone, email,
guardian data, internal ids, tenant/school ids, database identifiers, file paths,
or any document content. The LEVEL 3 row exists only to name what is always
reserved to the existing confidential delivery path (SPR-012 publication to known
recipients, portal access) — it is **not** a public-surface option.

### Interaction with VisibilityPolicy / VerificationPolicy

* `VisibilityPolicy` (SPR-012) governs what authenticated scopes (director,
  secretary, teacher, parent, student) may see of a document's *sections* inside the
  platform, with `self_only` enforcement for the self-scoped roles.
* The anonymous public verifier is a **genuinely new audience** that does not exist
  in the VisibilityPolicy map. Public verification introduces a **distinct
  verification scope** governed by a `VerificationPolicy` on the document
  (verification-enabled, disclosure level, allowed document types). It never
  inherits `*`/administrative sections from a VisibilityPolicy.
* Both policies are metadata on the document; enforcement of the public profile is
  the verification surface's own responsibility.

### Response shape

Verification returns a **verdict plus identity-confirming metadata** — it does not
host, stream, or download the document. Composing/downloading official files stays
with SPR-012 delivery. The semantics of the verdict are Decision 7.

Timing discipline: responses for LEVEL 0, invalid tokens, and revoked documents
must be computationally indistinct from successful lookups to frustrate
enumeration.

## Decision 4 — Revocation / Invalidation

**Chosen: YES — SPR-016 introduces formal REVOCATION, and REPLACED as a distinct
relational state.**

### Semantic vocabulary (these are NOT synonyms)

| State | Meaning | Public verdict | Reversible? |
| --- | --- | --- | --- |
| PUBLISHED | currently valid and published | authentic — published | n/a |
| ARCHIVED | no longer current but historically authoritative | authentic record — archived | no |
| REVOKED | formally withdrawn by the school | authentic record — officially revoked | **no** |
| INVALIDATED | internal integrity failure (checksum/content mismatch) | non-revealing failure — never "authenticated" | no |
| REPLACED | superseded by a successor document (attribute on the archived superseded document) | authentic — superseded by {successor number} | no |

### Revocation rules

* **Who**: only a principal holding the `document.revoke` capability. The
  permission surface follows the existing academic-communication permission group
  precedent.
* **Execution**: a recordable, audited action on the document aggregate. A reason
  (required category + free text) is captured; the verifier only ever sees the
  generic category, never the free text.
* **Effect**: forward-only transition from Published or Archived. The document
  becomes immutable (no new versions, no re-publication). The token and verification
  identity are preserved (Decision 2) so a previously distributed signature/QR
  keeps resolving — to a negative verdict.
* **Verifier experience**: "authentic record, officially revoked on {date}" — the
  verifier learns the revocation attaches to an authentic document without seeing
  why.
* **Audit**: every revocation is a documented event (actor, capability, reason,
  timestamp, document identity). Free text is school-staff/audit visibility only.

### Replacement

Replacement is **archive old + publish new**, not an edit. The superseded document
goes to Archived with a `replaced_by` reference to the successor's document number;
the verifier of the old token sees "authentic — superseded by {number}". The
successor keeps its own token and identity.

### What this ADR does not decide (implementation phase)

The exact persistence shape (column/table/event) of `revoked_at`, `revocation
reason`, and `replaced_by` is an implementation detail of SPR-016, constrained by
"no duplicate numbering authority" and "no duplicate lifecycle engine" below.

## Decision 5 — QR Architecture

**Chosen: B — the QR encodes a public verification URL that carries the opaque
verification token and nothing else.**

* Canonical payload form: `https://{verify-host}/v/{token}` (host finalized at
  implementation). The payload contains **only** the opaque token — no document
  number, no school code, no internal ids, no tenant identifiers.
* **Ownership split** (fixed boundary):
  * SPR-016 owns the **verification identity and its semantics** — what the QR
    payload is, the token, the URL contract, and the verification behavior.
  * SPR-012 owns **document rendering** — the visual QR is rendered by the existing
    renderer/blade substrate (the unused `qrCodeEnabled` affordance exists there for
    this) using the payload supplied by SPR-016. No duplicate rendering engine, no
    new PDF pipeline.
* The QR is **optional**, gated by the existing template flag `qr_code_enabled`.
* **Manual entry is always supported** — the token is typeable from the printed
  verification code; the QR is a convenience.
* **Signed QR URLs are rejected at this stage**: the token is already
  high-entropy bearer material and defense-in-depth is provided by rate limiting +
  hashing + uniform responses. Signing adds key-distribution and offline-verification
  complexity with no corresponding capability gain for the announced surface. This is
  revisitable in the Future Extension Boundaries section below.

## Decision 6 — Tenancy Resolution

**Chosen: B — central verification endpoint + opaque verification token resolves the
tenant.**

* **Resolution path (conceptual)**: token → SHA-256(token) → record mapping to
  `(school_id, document_id)` → read through a per-tenant, read-only verification
  contract on the resolved tenant's database. The resolved row's `school_id` is the
  peer of the tenant database suffix; the contract physically prevents reading any
  other tenant's data.
* **Guarantee**: school A can never retrieve school B's document unless the token
  genuinely belongs to B and the architecture authorizes that read. Token mapping is
  global to the central store; there is no "try school A, try school B" path because
  the token is the capability and resolves to exactly one tenant.
* **No school-code + document-number probing**: sequential document numbers
  (per-school, enumerable) are never a lookup key on the public surface. This closes
  the enumeration channel opened by "document number + school code" schemes.
* **Subdomains/domains** remain the **authenticated portal** surface and share
  nothing with the verification surface; a verification request never redirects to a
  school domain (redirects would leak tenant existence).

## Decision 7 — Document Lifecycle & Verification Semantics

**Chosen: minimal invariant — UNPUBLISHED DOCUMENTS MUST NEVER BE PUBLICLY
VERIFIED AS AUTHENTIC.**

Lifecycle states and their public verification verdicts:

| State | Public verdict | Notes |
| --- | --- | --- |
| Draft | no public record | internally incomplete |
| Generated | no public record | exists but never treated as issued |
| Reviewed / Approval pending | no public record | exists but not authoritative |
| Approved | no public record | *until published* |
| Published | authentic — published | currently valid; the only "currently valid" answer |
| Archived | authentic record — archived | historically authoritative; still verifiable |
| Revoked | authentic record — officially revoked | Decision 4 |
| Replaced (superseded) | authentic — superseded by {number} | Decision 4 |

* A verifier must be able to distinguish "**authentic but archived**" from
  "**currently valid/published**" — these are different answers about the same
  authentic record.
* Verification truth is the **document aggregate lifecycle status**, never
  `PublicationRecord` (which is soft-deletable and delivery-oriented). A deleted or
  re-sent delivery record must not change what a verifier learns.
* Unpublished states return the uniform LEVEL 0 response and never confirm that the
  document exists.

## Decision 8 — Identity Stability

**Chosen: A — the verification identity belongs to the AcademicDocument aggregate.**

* The token is bound at generation to the aggregate root and persists across every
  version of the document, every regeneration of generated files, archival,
  replacement and revocation.
* It is **not** bound to a specific `AcademicDocumentVersion` and **not** bound to
  any `PublicationRecord` — a version swap or a delivery-record deletion must not
  rotate or withdraw the verification identity.
* Content-level integrity (which version's content this document currently shows) is
  evidenced by `content_hash` and `GeneratedFile.checksum`; provenance and
  authenticity are the aggregate's verification record. Both coexist: hash proves
  "these bytes are what the school rendered", verification proves "this document was
  officially issued by this school".
* Historical verification remains possible for archived or superseded documents via
  their stable token (Decision 4/7).

## Cryptographic Scope

Decision-only; no library is committed by this ADR.

* **Integrity** — `content_hash` (SHA-256 of JSON content) and `GeneratedFile.checksum`
  (SHA-256 of bytes) already detect tampering of content. They prove *integrity* of
  a record, not *authenticity* of the record (any re-computed value collides when an
  attacker controls data).
* **Authenticity/provenance** — what a verifier needs is proof that the record is
  the school's official issuance. SHA-256 alone does not establish this. The
  verifiable claim is constructed from platform-side, tenant-isolated state plus the
  bearer token as knowledge of the capability; the token is therefore stored hashed
  (SHA-256, matching existing bearer-token precedent) and never transmitted in
  analytics/URL-completion tooling.
* **Non-enumerability** — high-entropy (≥144-bit) CSPRNG token; hashed at rest;
  uniform responses; rate limits (Decisions 2–3).
* **Confidentiality** — public responses restricted to Decision 3 metadata; no
  content.
* **Revocation** — terminal revoke transition with capability, recorded reason and
  audit (Decision 4).
* **Auditability** — verification events and revocation events are auditable records;
  audit never stores the plaintext token.
* Where cryptographic signatures or HMACs are later needed (offline verifier,
  signed QR), the choice of primitive and key ownership (school-held or platform-
  held) is a separate ADR, not assumed here.

## Security Invariants

* **I1** — Unpublished documents are never publicly verified as authentic.
* **I2** — Verification identity is non-enumerable; there is no sequential or
  brute-force path from public values to a verifiable record.
* **I3** — No cross-tenant verification: a token resolves to exactly one tenant and
  no request can read another tenant's record.
* **I4** — Public disclosure is limited to the minimum the document's verification
  policy permits (default LEVEL 2), enforced by the verification surface itself.
* **I5** — The document number is a public, non-secret identifier and is never the
  verification capability; it must not become a secret by annotation or context.
* **I6** — Hashes demonstrate integrity, not authenticity; SPR-016 never conflates
  checksum existence with verification.
* **I7** — Archived is not revoked: the two verdicts are semantically distinct and
  must be emitted distinctly.
* **I8** — Verification identity is stable for the life of the document aggregate;
  it never rotates with versions, files, publication records or replacements.
* **I9** — The legacy generated-document system is excluded from verification truth;
  nothing in SPR-016 reads or writes legacy models.
* **I10** — Verification reads are performed exclusively through the SPR-016
  read-only contract over the current AcademicCommunication substrate; direct domain
  coupling in Domain/Application is prohibited (see Implementation Constraints).
* **I11** — The token is stored hashed (SHA-256) at rest; the plaintext appears only
  at generation and inside document representations.
* **I12** — Public verification responses never reveal content, personal data or
  internal identifiers beyond the approved metadata set (Decision 3).
* **I13** — Revocation requires a capability, a recorded reason category, and an
  audit event; it is terminal and irreversible.

---

## Privacy Invariants

* P1 — Grades, transcripts, results, DOB, addresses, contact details, guardian data
  and internal/tenant ids are never present in public verification responses.
* P2 — The verifier learns only what the document's VerificationPolicy grants; a
  request does not raise a document's disclosure level.
* P3 — LEVEL 0 / invalid / revoked responses are indistinguishable in cost and shape
  to frustrate probing.
* P4 — Public verification does not make the school a document host; it returns
  verdicts and metadata only.
* P5 — Revocation free-text reasons are visible to school staff/audit only, never to
  the public verifier.

---

## Tenancy Invariants

* T1 — Verification resolution is central + opaque token; no school-code /
  document-number probing path exists on the public surface.
* T2 — A resolved token binds to exactly one tenant; reads execute against that
  tenant's data store through the read-only contract.
* T3 — Subdomains/domains are authenticated surfaces only; the public verification
  surface shares nothing with them and never redirects to them.
* T4 — Secret-free identifiers (document numbers) are never used as authorization
  or as lookup keys across tenants.

---

## Legacy-System Invariants

* L1 — SPR-016 must not use, read, or write `app/Models/GeneratedDocument`,
  `app/Models/DocumentTemplate`, `app/Services/DocumentGenerationService`, the legacy
  `app/Domains/Document` context, or legacy DocumentCenter views, unless a later ADR
  explicitly amends this boundary.
* L2 — SPR-016 consumes the current AcademicCommunication substrate exclusively,
  through the dedicated read-only contract/adapter defined in Implementation
  Constraints.
* L3 — No duplicate document-generation pipeline and no duplicate
  document-number authority may be created anywhere under SPR-016.

## Consequences

Positive:

* Third-party verifiers (employers, universities, government, other schools,
  parents) can verify documents they hold without credentials — the central use
  case.
* Document numbers remain public/display-only; the verification capability is
  non-enumerable and tenant-bound.
* Privacy is minimal by default and never leaks document content or personal data.
* Revocation gives schools a controllable, audited way to withdraw an official
  document.
* QR evolution is decoupled: SPR-016 controls semantics, SPR-012 controls pixels.

Negative / acceptance:

* A public surface is a permanent abuse target: rate limiting, hashing, uniform
  responses, and monitoring are ongoing operational duties, not one-time work.
* Verifiers of revoked/superseded documents get a semantic "authentic but no longer
  valid" answer, which some counterparties may initially misread.
* The central verify host adds a platform-level DNS/TLS/availability surface during
  implementation.
* Token hashing at rest means token recovery is impossible; loss requires issuance
  of a new document.

---

## Rejected Alternatives

1. **Document number as the public secret / verification key** — rejected: the
   number is sequential, enumerable, printed on the document, and already emitted as
   the verification code; making it a capability enables wholesale scanning.
2. **Sequential/internal ids as verification identities** — rejected: directly
   enumerable and cross-tenant hazards.
3. **Authenticated-only verification** — rejected: external verifiers are not
   platform users and cannot hold credentials.
4. **School-code + document-number lookup** — rejected: creates an enumeration
   oracle and a cross-school guessing channel.
5. **Full disclosure of document content / student records to the public** —
   rejected: privacy and data-governance violations.
6. **SHA-256 as authenticity** — rejected: hashes establish integrity only, not
   provenance; authenticity comes from tenant-isolated state plus the bearer token.
7. **Reviving `GeneratedDocument` / legacy document pipeline** — rejected: ADR-021
   and this ADR fix the current substrate as the single source of truth.
8. **QR containing internal DB ids / school codes / full URLs to tenant domains** —
   rejected: leaks infrastructure and breaks tenant isolation.
9. **Signed QR URLs at this stage** — deferred, not rejected permanently (see Future
   Extension Boundaries).
10. **Per-version or per-publication identity (token bound to a version or a
    PublicationRecord)** — rejected: instability across regeneration/replacement and
    soft-deletable delivery records.

---

## Implementation Constraints

Contract obligations placed on the future SPR-016 implementation:

* **C1 — Read contract**: SPR-016 must not import `AcademicDocument` (or other
  domain entities) directly from Domain/Application. A dedicated read-only
  verification contract/adapter over the AcademicCommunication substrate is the only
  allowed data path.
* **C2 — Rate limiting**: the public surface is rate-limited per IP and per token;
  bulk probing is structurally throttled.
* **C3 — Tenant safety**: resolution is central + opaque token (Decision 6);
  T1–T4 hold.
* **C4 — Non-predictable identity**: token ≥144-bit CSPRNG, generated once, hashed
  at rest (Decision 2).
* **C5 — Privacy-minimized responses**: only Decision 3 metadata; I4/I12 and P1–P5
  hold.
* **C6 — No duplicate generation**: SPR-016 creates no document-generation or
  rendering pipeline; L3 holds.
* **C7 — No duplicate numbering**: SPR-016 never issues, sequences or reuses
  document numbers.
* **C8 — Lifecycle truth**: verification reads the aggregate lifecycle status, never
  soft-deletable PublicationRecords.
* **C9 — Revocation authority**: revoke acts through the existing permission/
  capability pattern with recorded reason and audit (I13).

---

## Future Extension Boundaries

* Offline verifier / signed QR: requires a dedicated ADR choosing the primitive and
  key ownership; automatically disabled/augmented without invalidating the token
  scheme.
* Government verification services: separate ADR; the central endpoint is the
  integration seam, nothing ties this ADR to a specific provider.
* Portal-based verification for enrolled audiences: authenticated surface; out of
  scope of the public endpoint.
* Full-document on-line viewing (LEVEL 3 for authenticated parties): reserved to the
  SPR-012 delivery/portal path; never added to the public surface without a new ADR.
* QR renderer replacement on the SPR-012 substrate is independent of SPR-016
  semantics.

## Testing Requirements

The following must be proven during SPR-016 implementation (tests are out of scope
for this decision phase):

* **Enumeration resistance**: invalid tokens and unpublished documents yield uniform,
  indistinguishable responses.
* **Tenant isolation**: school A attempting to resolve school B's token returns the
  uniform failure; token mapping resolves to exactly one tenant.
* **Lifecycle matrix**: Draft/Generated/Reviewed/Approved → no public record;
  Published → authentic-published; Archived → authentic-archived; Revoked →
  authentic-officially revoked; Replaced → authentic-superseded.
* **Revocation capability + audit**: only `document.revoke` holders can revoke;
  reason recorded; audit event emitted; irreversible.
* **Privacy field absence**: public responses never contain forbidden fields
  (grades/DOB/contact/internal ids) — a contract-level assertion suite.
* **Token hashing**: plaintext token is not persisted; lookup only by hash.
* **QR payload contents**: payload is exactly `{verify-host}/v/{token}`, contains no
  document number/school code/internal ids.
* **Publication-record immunity**: deleting/editing a PublicationRecord does not
  change verification verdicts.
* **Rate limiting**: per-IP and per-token throttles engage as specified.

# ADR-013
# Class Council Engine Architecture

**Status:** Accepted

**Date:** 2026-08-06

**Decision Makers:**

- Solution Architect
- Backend Architect
- Academic / Domain Expert

---

# Context

A school's academic year ends with a class council: the teachers and the
principal meet, validate the published results of each student and take a
formal decision (promotion, repetition, orientation, conduct, distinction).
That decision is the academic truth the rest of the platform must respect — the
bulletin, the minutes and the transcript all depend on it.

In the previous architecture this responsibility was scattered: promotion
logic and "pass / fail" rules lived inside Assessment / Gradebook code,
decisions were not versioned or audited, and nothing prevented a downstream
engine from recomputing (and disagreeing with) a council outcome.

NexusSchool needs a **single academic-validation layer** so that:

- the council session has a **forward-only lifecycle** and a **published
  session is immutable**;
- a decision is **audited**, carries a **permanent code**, and — when it
  overrides the automatic decision — a **justification, an approval and the
  snapshot of the overridden automatic decision**;
- **confidential deliberations** are recorded but **never** exposed to
  downstream engines or rendered documents;
- every transition is **authorized** (capability-based), **school-scoped** and
  **audited**;
- downstream engines (Report Card, Academic Communication) read **only
  published decisions** through **domain contracts + adapters**.

SPR-010 (Gradebook, the source of the published standing), SPR-011 (Report
Card, the first consumer) and SPR-012 (Academic Communication, the publication
layer) established the DDD + Actions structure, the contract/adapter boundary
and the tenant-isolation conventions that this decision must follow.

---

# Problem Statement

How should NexusSchool model class council sessions and their decisions so
that:

- the engine is the **only** place academic validation happens;
- a session lifecycle is **forward-only** and **published sessions are
  immutable**;
- an **override of the automatic decision requires justification + approval +
  audit history**;
- **deliberations stay confidential** and can never reach a document;
- downstream engines consume **only published decisions**, and only through
  contracts (never by importing a council model);
- every query is **school-scoped** and every action **capability-gated**?

The model must not leak transition logic into the Eloquent model, must not let
the Filament layer bypass the application actions, and must not couple the
engine to any business engine's schema.

---

# Decision

Nexus adopts a **single CouncilSession aggregate root** with a forward-only
lifecycle, an application-owned automatic decision rule, and **contracts
instead of foreign-model imports** for every consumer.

```text
CouncilSession (aggregate root, forward-only status, school-scoped)
   ├─ CouncilDecision (optional student; null = whole class)
   │     code {session.reference}-%03d, decision_type, category
   │     override snapshot: automatic_decision_type/label, justification,
   │     approved_by/at, recorded_by
   └─ CouncilDeliberation (confidential; never exposed through a contract)

CouncilSessionStatus: draft -> convened -> published -> archived
                      (published/archived are immutable)
```

- The `CouncilSession` model holds **no transition logic**. All invariants
  live in **application Actions**, invoked only through the
  `ClassCouncilService` facade. Transitions are guarded by
  `CouncilSessionStatus::allowsTransitionFrom()` (`assertCanTransitionTo`).
- **Only a Convened session** accepts decisions and deliberations
  (`isDeliberating()`); published and archived sessions are immutable
  (`isImmutable()`).
- **Automatic decision rule** (`AutomaticDecisionService`), owned by this
  engine and never duplicated: no standing (or null overall percentage) → no
  automatic decision; `failedSubjects > 0` → Failed; `overallPercentage ≥
  passing_percentage` (school config) → Passed, else Failed.
- **Overrides:** a decision flagged `is_override` requires a justification and
  an approval (`OverrideApprovalRequiredException` otherwise), and snapshots
  the overridden automatic decision (`automatic_decision_type` /
  `automatic_decision_label`) so the audit history always shows what the
  automatic rule would have said.
- **Decision code:** `{session.reference}-%03d`, unique per school — a
  permanent reference usable on bulletins and minutes.
- **Confidentiality invariant:** `CouncilDeliberation` records are private to
  the council domain. Contracts expose **only published decisions** — never a
  deliberation and never a convened (unpublished) decision.
- **Consumers (read-only) through contracts:**
  - Report Card — `decisionsForStudent(school, student, year, term)` → the
    latest **Published/Archived** session covering the student's class and
    period (`code / label / decision`).
  - Academic Communication — `publishedDecisions(school, session)` → the
    **Published/Archived** decisions of one session (`id / summary / category /
    studentId / decisionDate / recommendation`) for the minutes.
- **Authorization** is centralized in `HandlesClassCouncilAuthorization` with
  8 capabilities (`class-council.view/create/update/convene/decide/publish/
  archive/delete`), capability-based (never role-based) with the `super_admin`
  bypass and school scoping on every check.
- Deletion is disabled on the aggregate; history is preserved via the
  `council_*` tables and the append-only audit journal
  (`ClassCouncilAuditLogger`).

# Alternatives Considered

## Option 1

Each business engine decides for itself (Assessment marks a student "failed",
Gradebook keeps its own promotion logic, Report Card guesses the outcome).

### Advantages

- No new engine to build.

### Disadvantages

- The same academic truth is duplicated and drifts across engines.
- No council lifecycle, no audit, no approval — an override is just a field.
- Downstream engines recompute instead of reading the council's decision.
- No permanent decision code shared by bulletins and minutes.

---

## Option 2

A decisions table with no session lifecycle (only "passed / failed" flags).

### Advantages

- Simple to write and to read.

### Disadvantages

- No convening / publication flow; nothing distinguishes a draft from the
  official validation.
- No immutability: published decisions can be silently edited.
- No deliberation records, no audit trail, no approval for overrides.
- No permanent code and no contract boundary — consumers import the model.

---

## Option 3 (Chosen)

Single `CouncilSession` aggregate + forward-only lifecycle + contracts.

### Advantages

- One canonical academic-validation layer.
- Provable immutability of published sessions; audited, approved overrides.
- Deliberations stay confidential by construction (never on a contract).
- Downstream engines read only published decisions through contracts — the
  dependency graph stays acyclic.
- Tenant isolation applied on every query; capability-based authorization.

### Disadvantages

- More tables and more moving parts than a "flags" table.
- Business data (standing, enrollments, frame) must be adapted (contract →
  adapter) before use.
- New decision categories require an enum case + label.

---

# Consequences

All academic validation in NexusSchool now goes through
`ClassCouncilService`.

This concerns:

- Filament resources (`CouncilSessionResource` + 3 pages) under "Conseil de
  classe"
- Authorization and permission definitions (`class-council.*`)
- The Report Card engine (bulletins render the published decisions via
  `ClassCouncilContract`) and the Academic Communication engine (minutes render
  the published decisions via `ClassCouncilContract`)
- Future sprints that need an academic decision (transcripts, certificates)
  — they will consume the published decisions through the same contract
  boundary.

New validation features must preserve the forward-only lifecycle, published
immutability, the override (justification + approval + snapshot) rule and the
confidentiality of deliberations.

---

# Positive Impacts

- Single, audited, tenant-isolated academic-validation layer.
- Published sessions are immutable; overrides are justified, approved and
  snapshotted.
- Confidential deliberations can never reach a rendered document.
- Permanent decision codes shared by bulletins and minutes.
- Contract boundary keeps the engine decoupled from every consumer.

---

# Negative Impacts

- Larger schema (3 migrations) and more code than a decisions flag.
- Business data must cross a contract/adapter boundary before use.
- Consumers get decisions only after a session is published — a convened
  (unpublished) decision is invisible downstream by design.

# Implementation Notes

Implemented under `app/Domains/ClassCouncil`:

- `Infrastructure/Models/CouncilSession` — aggregate root (reference, forward-only
  status, timestamps, scopes, transition guard).
- `Application/Actions/*` — 6 explicit actions (create, convene, record
  decision, record deliberation, publish, archive).
- `Application/Services/ClassCouncilService` — the only public entry point;
  `AutomaticDecisionService` owns the automatic decision rule.
- `Domain/Enums/CouncilSessionStatus` / `CouncilDecisionType` /
  `CouncilDecisionCategory` — lifecycle and catalogs.
- `Domain/Contracts/*` + `Infrastructure/Contracts/*` — the cross-domain
  boundary, bound to adapters in `ClassCouncilServiceProvider`.
- `Domain/References/*` — verbatim snapshots (student, enrollment, period,
  standing, automatic decision, review item).
- `Infrastructure/Policies/CouncilSessionPolicy` +
  `Domain/Traits/HandlesClassCouncilAuthorization` — capability-based
  authorization.
- `Domain/Events/*` + `Infrastructure/Listeners/ClassCouncilAuditLogger` —
  audit + journal.
- Consumers: `ReportCard\Infrastructure\Contracts\ClassCouncilAdapter` and
  `AcademicCommunication\Infrastructure\Contracts\ClassCouncilAdapter`.

Schema: 3 migrations (`2026_08_06_000015` → `000017`).
